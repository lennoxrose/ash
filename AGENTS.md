# AGENTS.md

Ash is a from-scratch programming language in C (no external dependencies).
Two projects: `ashvm/` (lexer → compiler → bytecode VM, the engine) and `kiln/` (separate `.ash` → native ELF/PE compiler).
The codebase is modular, reusable, and navigable by path alone. Follow the structure below exactly.

---

## 1. File-type trees (the core rule)

Every subsystem separates file types into **four mirrored trees**. Never mix them in one directory.

```text
subsystem/
├── C/   sources        (.c)
├── H/   headers        (.h, .def)
├── D/   dependency files (.d, generated by -MMD; kiln only)
└── O/   objects        (.o, generated)
```

- The docs write `.C/.H/.D/.O` as concepts. The real files are **lowercase** (`.c .h .d .o`). Do not create uppercase extensions.
- One module = the same relative path in every tree, only the tree dir and extension differ:

```text
kiln/src/codegen/C/expressions/expr.c
kiln/src/codegen/H/expressions/expr.h
kiln/src/codegen/D/expressions/expr.d
kiln/src/codegen/O/expressions/expr.o
```

- A header without a `.c` (e.g. `*_internal.h`, `value.h`) still lives in `H/<feature>/`.
- `ashvm` has no `D/` tree (its Makefile makes no dependency files). Don't add one unless you also add `-MMD` there.
- Includes are `src`-relative (`-Isrc`): `#include "codegen/H/expressions/expr.h"`.

## 2. Multi-language modules

Ash may use additional implementation languages where they are genuinely the best tool: C for the core/VM/compiler, C++ for GPU/platform code, Rust for memory-safe components, Fortran for numerical/scientific code, Zig for small low-level libraries, and assembly only for measured hot loops.

**The boundary is always the C ABI.** Ash, `ashvm`, and `kiln` only call C-compatible symbols. Every non-C language module must compile to a static library (`.a`) or shared library (`.so`/`.dll`) with `extern "C"` / C-ABI exports; it must never leak language-specific runtime types, exceptions, panics, or memory ownership across the boundary.

### Language source trees

Each implementation language gets its own **top-level source tree beside `C/`**, named by its lowercase language name. Do not put Fortran, Rust, C++, Zig, or assembly sources inside `C/`.

```text
subsystem/
├── C/         C sources (.c)
├── Cpp/       C++ sources (.cc/.cpp)
├── Rust/      Rust sources (.rs) + Cargo.toml when applicable
├── Fortran/   Fortran sources (.f90/.f)
├── Zig/       Zig sources (.zig) + build.zig when applicable
├── Asm/       assembly sources (.s/.S)
├── H/         C headers / public C-ABI contracts (.h)
├── D/         dependency files (kiln only)
└── O/         C objects and language build outputs that follow the C layout
```

- Use the exact folder names `Cpp/`, `Rust/`, `Fortran/`, `Zig/`, and `Asm/`. Keep them capitalized to distinguish a language tree from a feature folder.
- A non-C module mirrors the same feature path as its C counterpart:

```text
kiln/src/runtime/C/collections/matrix.c
kiln/src/runtime/Fortran/collections/matrix.f90
kiln/src/runtime/H/collections/matrix.h
kiln/src/runtime/O/collections/matrix.o        # C object
kiln/src/runtime/O/collections/matrix.f90.o    # Fortran object, if built per-file
```

- For Rust, keep the crate at the language root or feature root, for example `kiln/src/runtime/Rust/crypto/Cargo.toml`; its generated artifacts belong in that crate's own target output, not in `C/`, `H/`, or `D/`.
- For C++, use `.cc` or `.cpp` in `Cpp/` and expose only a C ABI through a header in `H/`. Never include C++ headers from C code.
- Assembly belongs in `Asm/` and must be justified by a benchmark or platform requirement; prefer C, C++, Rust, Zig, or Fortran otherwise.

### Public interface rule

Every cross-language module needs:

1. A C header in the matching `H/<feature>/` folder declaring the stable C ABI.
2. An implementation in the appropriate language tree.
3. A clear ownership contract in the header comment: who allocates, who frees, error handling, thread safety, and whether pointers may be retained.
4. A test that calls the public C ABI from Ash/C, not an implementation-language-internal test only.

Example contract:

```c
/* H/collections/matrix.h
 * Matrix multiplication backed by Fortran/BLAS-style code.
 * Caller owns input and output buffers; `matrix_multiply` does not retain them.
 * Returns 0 on success, non-zero on dimension/allocation failure.
 */
int matrix_multiply(
    const float *a, size_t a_rows, size_t a_cols,
    const float *b, size_t b_rows, size_t b_cols,
    float *out);
```

### Build rules

- One top-level build entry point must build every language. Do not require agents or users to run separate hidden build commands.
- C sources continue to follow the existing `C/ → O/` and `C/ → D/` Makefile mapping exactly.
- Non-C build systems (CMake, Cargo, `gfortran`, `zig build`, assemblers) must be invoked from the relevant subproject Makefile and place their final C-ABI library in a predictable project-local output location.
- Never commit generated build artifacts, object files, `.d` files generated by a foreign toolchain, or language package locks unless the project already intentionally tracks them.
- A language module must degrade cleanly: if its toolchain is unavailable, the build must either provide a documented C fallback or fail with a clear message. Do not silently omit functionality.
- Add a new language only when it has a distinct, justified responsibility. Do not add a language merely because it is possible.

### When to use which language

| Language | Use for | Avoid for |
|---|---|---|
| C | Core runtime, VM, compiler, portable glue, C ABI boundaries | Complex safe abstractions that Rust handles better |
| C++ | GPU, graphics, platform-specific acceleration | Public APIs; keep the exported surface C-only |
| Rust | Parsing, crypto, allocators, memory-safe components | Trivial glue where C is simpler |
| Fortran | Dense linear algebra, numerical/scientific kernels | General application logic |
| Zig | Small low-level libraries with easy C interop | Another general-purpose runtime |
| Assembly | Measured SIMD/hot loops, platform intrinsics | Anything without a benchmark proving the need |

## 3. Feature folders and size

- No directory holds more than about **10–20 files**. Counted per directory, per tree.
- Small subsystems (`lexer`, `elf`, `pe`, `diagnostics`, most of `ashvm`) use `C/` `H/` `D/` `O/` directly. Large ones add feature folders **identically in all trees**:

```text
codegen/C/expressions/  codegen/H/expressions/  codegen/D/expressions/  codegen/O/expressions/
```

- Feature names are short, lowercase, meaningful: `expressions statements declarations functions runtime collections strings builtins io platform control_flow`. Never `misc/ stuff/ other/ random/ things/`.
- When a directory outgrows the limit, split by real responsibility and mirror the split in every tree. Never just keep adding files. Do not split artificially either: cohesive modules, not the smallest files.
- For multi-language modules, mirror feature folders across the relevant language trees too. A Fortran module in `runtime/collections/` lives at `runtime/Fortran/collections/`, not in an unrelated top-level folder.

Current layout (extend it, don't flatten it):

| Subsystem | Feature folders |
|---|---|
| `kiln/src/codegen` | `emit expressions functions runtime collections strings builtins io platform` |
| `kiln/src/parser` | `core statements declarations imports` |
| `kiln/src/{lexer,elf,pe,diagnostics,app}` | flat `C/ H/ D/ O/` |
| `ashvm/src/{app,lexer,value,vm,compiler,builtins,diagnostics}` | flat `C/ H/ O/` (`app/H/common.h` is the shared header) |

## 4. Build

### Build commands (always use these)

Always build and clean through the root Makefile. Do not construct long per-language/per-file compiler commands unless debugging a specific toolchain issue—and explain why in that case.

From the repository root:

```bash
make            # clean + build all subprojects (ashvm, kiln, forgepack, ...)
make clean      # clean all subprojects
make @ashvm     # clean + build only ashvm
make @kiln      # clean + build only kiln
```

- Use `make` for normal verification after changes.
- Use `make @<subproject>` when only one subproject was changed, to save time and tokens.
- Use `make clean` before a full rebuild or when generated files/build configuration may be stale.
- Never replace these commands with a giant direct `gcc`/`gfortran`/`cargo`/`zig` command in normal work.
- New languages and build systems must be wired into their subproject Makefile so the root `make`, `make clean`, and `make @<subproject>` commands continue to work unchanged.

### General build rules

- Makefiles derive `O/` and `D/` paths from each source's `C/` path by replacing `/C/` → `/O/` / `/D/`. So C source paths must contain exactly one `/C/` directory.
- New `.c` file → add it to `KILN_SRC` / `ASHVM_SRC`. Its header goes in the matching `H/` folder.
- New non-C source → add it to the correct language tree and register it with that language's build step; expose it through a C header in `H/`.
- `.o` is gitignored. Every `O/` directory has a `.gitkeep` so the empty trees stay in git. **Add one to any new `O/` directory.**
- `make clean` deletes only `*.o`/`*.d` files, never directories (this protects `.gitkeep`). Keep it that way. Language-specific clean rules may remove their own generated artifacts, but never source files or `.gitkeep`.
- kiln's `.d` files are generated by the build and currently tracked. Never hand-edit them.
- Flags are `-Wall -Wextra -std=c11 -O2`. New C code builds warning-free. Non-C code must build cleanly under its own toolchain's recommended warning settings.

## 5. Tests

Same discipline applies to tests:

```text
<project>/tests/
├── scripts/                      run_regression.sh, imports_*_check.sh (all .sh files live here)
└── cases/
    ├── <feature>/*.ash           one folder per feature (basics, control_flow, errors, functions, collections, strings, io, imports, ...)
    └── imports/{fixtures,ash.libs}
```

- New test → `tests/cases/<feature>/name.ash` (≤ 20 files per folder, split by feature if needed). Never in `tests/` root.
- All `.sh` files go in `tests/scripts/`. They `cd` to the project root (`../..`) and use `tests/cases/...` paths.
- `fixtures/` and `ash.libs/` stay in `cases/imports/`: imports resolve relative to the **entry file's directory**, so they must sit beside the test that imports them.
- Test names are unique across features (the runner keys outputs by basename).
- Every non-C module needs at least one regression test through its public C ABI. Test error paths, allocation ownership, and invalid inputs—not only the happy path.

Verify (from the repo root):

```bash
kiln/tests/scripts/run_regression.sh baseline   # BEFORE a change
kiln/tests/scripts/run_regression.sh check      # AFTER; must be byte-identical unless the change is intentional
ashvm/tests/scripts/run_regression.sh baseline|check
```

Performance-sensitive work (`ashvm/src/vm`, fused ops in `compiler`, Fortran/assembly kernels) also needs the `ashvm/benchmarks/` runs before and after (reference: `fib(30)` ≈ 0.06s, sum to 20M ≈ 0.12s). Don't regress. The planned Lua-style syntax belongs in the lexer and compiler and must add no per-instruction cost to the VM (see `plans.md`).

## 6. Adding, moving, reusing

**Adding a C module `example` to expressions:** create `C/expressions/example.c` + `H/expressions/example.h` (+ `D/`/`O/` are generated), register the `.c` in the Makefile, add `.gitkeep` if the `O/` folder is new. Never drop it in the subsystem root.

**Adding a non-C module:** create the language source under the matching language tree, for example `Fortran/collections/example.f90`, create or extend the public C header in `H/collections/`, register the build step, and add a C-ABI regression test. Never place non-C sources in `C/` or expose non-C types in a public header.

**Moving a module:** move the whole set (`C/ H/ D/ O/` entries, plus the matching language-tree sources) together to the same new relative path. Afterwards:

- update `#include`s and path mentions in comments/READMEs
- update the Makefile and language-specific build configuration
- regenerate `.d` files (clean build)
- grep for the old path
- build and run the regression suites. Never leave a refactor half-finished.

**Reuse:** before writing code, search for an existing module. Extend the owner when the behavior belongs there; create a new module only for a distinct responsibility. No duplicate compiler/parser/runtime logic.

**Dependencies:** one-way, no cycles: `lexer → parser/compiler → vm/value/codegen → builtins/runtime`. Diagnostics is shared. If two modules are tightly coupled, revisit their boundary before adding more coupling. Cross-language dependencies must point toward the C ABI header, never directly into another language's internals.

## 7. Agent rules

MUST:

- Inspect the existing structure before creating files; reuse modules.
- Keep `C/ H/ D/ O/` separate and mirrored, `.c`/`.h` paired, directories ≤ ~20 files.
- Keep non-C implementation sources in their own language tree (`Cpp/`, `Rust/`, `Fortran/`, `Zig/`, `Asm/`), mirrored by feature where applicable.
- Expose every cross-language module through a stable C ABI header in `H/`; document ownership, errors, and lifetime rules.
- Use `make`, `make clean`, or `make @<subproject>` from the repository root for builds and cleans; do not invent long direct compile commands for routine work.
- Keep tests in `tests/cases/<feature>/` and scripts in `tests/scripts/`.
- Update all references, build files, and language build steps after moving files; build and test after structural changes.
- Keep structural refactors separate from language/behavior changes so regression diffs stay meaningful.
- Write changelog entries newest-first at the **top** of `CHANGELOG.md`, headed `## YYYY-MM-DD (topic)`. Don't use `changes.sh`: it appends to the bottom.
- Match the surrounding code's style, naming and comment density; update `README.md` when layout or user-visible features change.

MUST NOT:

- Mix `.c/.h/.d/.o` in a directory, or put files in a flat dump.
- Put Fortran, Rust, C++, Zig, or assembly sources inside `C/`.
- Expose C++ classes, Rust types, Fortran module state, or language-specific exceptions across the C ABI.
- Create `misc/stuff/other` folders to hide file counts.
- Bypass the root Makefile with long manual compiler/toolchain commands during normal development.
- Break the mirrored layout, the C ABI boundary, or leave the build or tests broken.
- Commit unless the user asks.

**Keep modules reusable. Keep directories small. Keep C/H/D/O trees separated and synchronized. Keep every language behind a clean C ABI. Use the root Makefile commands.**
