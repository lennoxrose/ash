## 2026-10-19 (for-each over an ArrayList: Java's ConcurrentModificationException, same in ashvm and kiln)
- **What it was**: growing or shrinking a list inside a for-each over it behaved differently per backend. `ashvm` re-read the length every step (so `for (x : xs) xs.add(..)` kept going, as long as the list grew), `kiln` read the data pointer and the count once (it stopped at the old count, read past the end after a `remove`, and walked a freed array after the list was reallocated by an `add`).
- **Now**: the front end lowers a for-each over an `ArrayList` / `List` the way Java's iterator behaves. The list is read by index, the loop ends when the position equals the current size, and if the size changed since the loop began, asking for the next element throws `ash.util.ConcurrentModificationException` (a new `RuntimeException` in the compiler's core library, `jcore/C/core_lang.c`; import it to catch it). So adding to the list throws at the next step, removing the second-to-last element just ends the loop, removing the last one throws, `set` is fine, and `break` right after a change is fine. Checked against the output of a real JDK for all of these. Arrays are unchanged (their size cannot change). Not mirrored: Java counts modifications and the lowering compares sizes, so an `add` followed by a `remove` that leaves the size equal is not detected, and `sort` during the loop does not throw.
- **Regions**: `region.c` no longer refuses a for-each whose iterable is a list declared in the loop body (the stale-pointer reason is gone). Such lists, their elements and the loop variable die with the iteration; a loop that grows its own list is not a region (a `list.add` there targets a variable that is not the loop's own), and the exception is raised outside the body, before the next iteration's checkpoint.
- Tests: `front/tests/cases/run/run_foreach_modify_j.ash` (both backends), `kiln/tests/cases/ownership/RegionForEachLocal.ash` (8 region loops, poisoned); `RegionForEachEscapes.ash` lost its `innerList` case, which is a region now.

## 2026-10-19 (Mnemosyne: loop regions with try / catch / finally)
- **A loop body (or the body of a pure callee, see the entry below) may contain `try` / `catch` / `finally`** (`kiln`, Linux static builds, `memory-safety: on`; `front/src/jown/C/region.c`). ## 2026-10-19 (Mnemosyne: loop regions with calls to pure project methods)
- **A loop may now call project methods that provably keep nothing they allocate** (`kiln`, Linux static builds, `memory-safety: on`; `front/src/jown/C/region.c`, new `JMethod.rg_pure`). The callee must be fixed at compile time (`static`, `private` or `final`; no constructor, no varargs, no generics), belong to the project (not `ash.*`), take only primitives and Strings and return a primitive, and its body must pass the rules of a loop body: every reference it stores goes to one of its own locals or parameters (a String, or an array / list that starts fresh), only primitives are written to fields, static fields and outer arrays, no project constructor, lambda, `try`, `switch`, `throw` or for-each over anything but a native array / list, and every call in it is in turn such a method or one of the harmless library calls. It is checked once per method (transitively); recursion, direct or through a cycle, is never accepted, and anything the analysis cannot see through (an overridable instance method, an interface call, an object argument) leaves the calling loop an ordinary loop. Since everything the callee allocates is unreachable once it returned, the region of the calling iteration reclaims it; a loop whose own body allocates nothing but which calls an allocating pure method is a region too. A call receiver (`this`, a local object, a class name) is checked like any other expression.
- **Effect**: `total += width("item-" + i)` over 2 million iterations, with `width` building a String and an `int[16]`, runs in 10 MB (61 MB with `KILN_NO_REGIONS=1`).
- Tests: `RegionCalls.ash` (11 region loops: static chains, `private` / `final` instance methods through `this` and through an object, `long` / `double` / `bool` / `char` results, String parameters, a callee with its own loop and arrays, a loop that only calls) and `RegionCallEscapes.ash` (0: callees that keep a result in a static field, an array or a list, return a String, take an array, keep their argument, recurse directly or mutually, call an impure method, `throw`, `try`, use a lambda or a `StringBuilder`, are overridable, or are public instance methods of a class that nothing extends); `region_check.sh` also checks the memory figures above.

## 2026-10-19 (Mnemosyne: loop regions for for-each)
- **A for-each over an array or an `ArrayList` can now be a region loop** (`kiln`, Linux static builds, `memory-safety: on`), under the same rules as the other loops (`front/src/jown/C/region.c`, `jlower/C/lower_stmt.c`). The checkpoint is taken after `each` has bound the loop variable, so the variable and the elements it refers to (all older than the iteration) survive the rewind; the array / list is evaluated once before the first iteration, which is outside the region, so for the loop itself the iterable may be any expression (`"a,b".split(",")`, `m.keys()`, a project call). Only the native array / `ArrayList` / `List` types qualify: any other `Iterable` runs project code in `hasNext` / `next`, and `Stream` is left alone.

## 2026-10-19 (Mnemosyne: loop regions in kiln)
- **A loop whose body keeps nothing it allocates past the iteration now gives it all back at once** (`kiln`, Linux static builds, `memory-safety: on`). The heap pointer is saved at the start of every iteration (`mem_region_enter`) and moved back at the end (`mem_region_leave`), which the todo list (`heap_checkpoint` / `heap_reset`) had left unwired because an unsound version corrupts memory instead of leaking. The analysis (`front/src/jown/C/region.c`) is deliberately narrow so that it can be read off the body: no call into project code (a callee may keep an argument or allocate into a field), no project constructor, lambda, `try`, `switch`, `throw` or for-each; the calls that remain cannot keep anything (String methods that read, `Math`, `println` of primitives and Strings, and `add` / `get` / `set` / `remove` / `size` on an `ArrayList` declared in the body); a reference is only ever stored into a variable declared in the body (a String, or an array / list that starts as a fresh one and is only given fresh ones), never into an outer variable, a field, an element of an outer array or an outer list (primitives may leave the iteration freely); `return` and `break` skip the rewind, which only leaves the memory allocated. The condition and update of the loop run outside the region.
- **Free lists**: a rewind also empties the free-list table (a block freed inside the region would lie beyond the heap pointer and be handed out again over newer data); blocks freed before the region are given up, a leak and never an overlap.
- **Effect**: a loop of 2 million iterations with String concatenations, a `substring` and an `int[8]` runs in 10 MB (155 MB with `KILN_NO_REGIONS=1`).
- **Checking it**: `KILN_REGION_POISON=1` when compiling overwrites the reclaimed bytes with `0xDD` before each rewind, so any value used after its iteration shows up as garbage (forcing the loop below to be a region prints empty lines). `hearth/kiln/tests/scripts/region_check.sh` expects `RegionLoops.ash` to contain 12 region loops and `RegionEscapes.ash` (outer variable, outer array, field, outer list, a callee that keeps its argument, lambda capture, `throw`, for-each, `switch`, `StringBuilder`, alias of an outer array, ...) to contain none, compares both with `ashvm` under poison and without regions, checks the 10 MB / 155 MB difference, and runs the whole regression suite with poison on (all pass); the ownership fuzzer with `KILN=1 KILN_REGION_POISON=1` also ran clean (about 40 region loops in its first 60 programs). Debug switches: `ASH_REGION_TRACE=1` prints the region loops, `=2` also why a loop is not one; `KILN_NO_REGIONS=1` turns the feature off. Windows (PE) output does not use regions: it could not be checked here (the Unicorn emulator is not installed).
- Not done: regions for loops that call project code (needs an escape summary per method), for-each, `try`, or maps, and in `ashvm` (it has no bump heap).
- Also fixed (slice before): the ArrayList-size prescan read a field of whatever a name resolved to; valgrind found it, it now only looks at local names.

## 2026-10-19 (Mnemosyne: use before assignment in the first pass of a loop)
- **`int c; for (..) { print(c); c = i; }` is a compile error** (`variable 'c' is used before it is assigned: the first pass through the loop reaches this use before any assignment`). Before, the back edge made `c` "assigned on some path" at the loop head, so the first iteration's read was missed. Now the first pass over an outermost loop (which starts from the exact state on entry) is judged on the straight-line part of the first iteration: the loop condition (`while (c < 3)`), then the body's statements up to the first branch with a jump, `switch`, inner loop, `try`, `break`, `continue` or `return`. An `if` without any jump in it keeps the straight-line part going (what it assigns still counts as an assignment on some path). A use behind a condition, `&&` / `||`, `?:`, a lambda, a `try` with a catch, in an inner loop, or after a `continue` is still not reported, because an earlier iteration may have assigned the variable (`if (!first) sum += c;`).

## 2026-10-19 (Mnemosyne: sizes of ArrayLists in the range checks)
- **`l.get(i)`, `l.set(i, v)` and `l.remove(i)` are checked** in `memory-safety: on` projects: an `i` that is always negative, or always at or past the known size of `l`, is a compile error (`list index is always out of bounds here: the index is 2 and the list size is 2`). The size is followed for a `List<T>` / `ArrayList<T>` local that starts as `new ArrayList<>()` (size 0): `add(x)` / `add(i, x)` add one, `remove(i)` / `removeLast()` take one off, branches and loops join the sizes like the integer ranges, and `l.size()` evaluates to the known size in other checks (`l.get(l.size())`). Passing it to a call (also `&l` / `&mut l`), `T k = l`, a for-each over it, `return l`, `sort`, `subList`, `forEach`, `stream` or any capture drops the local from the checks for the whole method. In a `try` the mutations are forgotten for the catch handlers like assigned integers.

## 2026-10-19 (Mnemosyne: use of a local that nothing assigned)

## 2026-10-19 (Mnemosyne: String lengths, array fields, switch cases in the range checks)
- **`s.charAt(i)` is checked** in `memory-safety: on` projects: an `i` that is always negative, or always at or past the known length of `s`, is a compile error (`string index is always out of bounds here: the index is 5 and the string length is 3`). ## 2026-10-19 (Mnemosyne: kiln and ashvm free the rows of `new T[a][b]`)
- **Rows of a two-dimensional array are freed with it.** A sole-owner `T[][]` local or owned field built by `new T[a][b]` (or `new T[a][]` with fresh `new` rows stored one by one) now gives its rows back before the outer array (`mem_free_elems` on a `T[][]`), in `ashvm` (`free` of each row) and in `kiln` (rows go back on the array free lists). ## 2026-10-19 (Mnemosyne: value ranges, compile-time bounds / overflow / division checks)
- **Rust interval engine in `mnemo.a`.** The flow state now also carries what is known about `int` / `long` locals (value ranges) and array lengths, with the same save / restore / join rules as the moved set: a fact only survives a join when both paths know it. ## 2026-10-18 (Mnemosyne: mnemo.a, freeing sole-owner values)
- **`bin/lib/mnemo.a`** (`hearth/mnemo`, Rust, C ABI in `mnemo/H/flow/flow.h`) is linked by both `ashvm` and `kiln`. It holds the move-flow engine of the ownership pass: moved sets, dead paths and the snapshots/joins at branches and loops. `front/src/jown` walks the typed AST and reports events to it. Built by `hearth/mnemo/Makefile` (cargo; a missing toolchain is a hard error pointing at `tools/install.sh`), wired into the `ashvm` and `kiln` Makefiles. C-ABI regression: `mnemo/tests/scripts/run_regression.sh`.
- **Freeing, `memory-safety: on` projects, `ashvm` only.** `jown` proves which locals are the sole owner of a fresh String (non-constant `+`) or array (`new T[n]`, `{..}`) and are only read (index, `.length`, operands, String methods returning primitives, print args, for-each). Lowering frees those with the new builtin `mem_free(x)` at the end of the block, before `return`/`break`/`continue` (the return value is computed first), and before a reassignment (`s += x`). Concatenation temporaries (an inner `a + b`, `str(int)`) are freed by `mem_cat(a, b, flags)`; `new T[n]` uses `__newarr1` so no dims array leaks. Everything else is left alone: leaking is safe, freeing a shared value is not. `kiln` lowers none of this yet (`jl_drops`), so its IR is unchanged until it has a free-list allocator.
- **Objects are freed too.** `T o = new T(..)` is a sole owner when `T` is a plain class (superclass Object, no default-method interfaces, not a Throwable/enum) and neither its constructor, field initializers, nor any method called on `o` lets `this` escape (checked transitively in `jown`; lambdas, `return this`, passing `this`, and call cycles count as escaping). `o` may only be read through fields, those methods, and `==`/`!=`. `mem_free` frees the object's map (keys and tables); field values are left alone. Test: `ashvm/tests/cases/ownership/OwnFreeObj.ash` (also clean under AddressSanitizer).
- **Borrows and call moves** (`memory-safety: on`). `&x` is a shared and `&mut x` an exclusive borrow of a local, written only as a call argument (parser `unary`, checker `check_unary`; a borrow lowers to the variable itself, so it costs nothing at run time). Passing a plain owning local to a project method or constructor now moves it; library and native calls only look at their arguments and never move. In one call an exclusive borrow excludes every other use of the same variable (`f(&mut x, &x)`, `f(&mut x, x)`, `x.m(&mut x)` are errors); `&x` anywhere else is an error. A lent variable is never freed by the sole-owner pass, since the callee could keep it. Tests: `OwnBorrow`, `OwnMovedCall`, `OwnBorrowConflict`.
- **Ownership transfer through `return`.** A call to project code (static, private, final, or a class nothing extends) whose every `return` hands over a fresh String / array, or a local that is its sole owner, yields a fresh value: the caller's `String s = build(i)` is freed like a local concatenation, and the callee skips freeing the local it returns (`front/src/jown`, `returns_fresh`). A method that can return an alias (a field, a parameter) is never treated as fresh. Test: `OwnFreeReturn.ash`.
- **`memory-safety` now defaults to `on`** (goals.md): `JOWN_DEFAULT_ON` is 1, and a project without `ash.pkg` is the entry file's directory. `memory-safety: off` in `ash.pkg` restores the old behaviour exactly. With it on by default the whole `ashvm` regression (all front corpus programs and examples) runs with freeing active, with byte-identical output, also under AddressSanitizer; `kiln`'s suite passes too. Source changes this needed: `examples/Desktop.ash` and `Generics.ash` lend with `&`, `run_oop_j.ash` uses `g` after `b` was moved into it, and `equals`/`compareTo` never consume their argument.
- **`System.free(x)` for `memory-safety: off`** (goals.md): lowers to `mem_free(x)`; it is an error in a project with memory safety on. `ashvm` frees the String, array or object; `kiln` has a `mem_free` builtin that does nothing until it has an allocator that can free. Tests: `tests/cases/memoff/` (both engines, own `ash.pkg`), `OwnFreeDenied.ash`.
- **Fixes found by adversarial tests** (`OwnFreeTry`, `OwnFreeAlias`, run under AddressSanitizer): `return` inside `try`/`finally` freed locals before the finally body read them (the finally bodies now run first, then the frees); `break`/`continue` under a `finally` no longer free.
- **Factory methods hand over objects.** `returns_fresh` also covers a plain object: every `return` must be `new T(..)` of one class (or a sole-owner local of it) and the declared return type exactly that class, so `Point p = make(i)` is freed like `Point p = new Point(..)`; a method returning two classes, a supertype, or an alias (a static, a field) is never fresh. Test: `OwnFreeFactory.ash`.
- **`apm` knows `memory-safety`.** It is a header key of `ash.pkg` (`on` | `off`): `apm new` / `apm init` write `memory-safety: on`, and every rewrite of `ash.pkg` (`apm add`, `apm license`, ...) keeps it. Before, any rewrite silently dropped the key, which would have flipped an `off` project to the default.
- **Constant folding through finals.** The constant-overflow check now sees through `final` int locals and `static final` int fields with constant initializers, so `Integer.MAX_VALUE + 1`, `final int n = 100000; n * n` and `BIG + BIG` are rejected too (`tests/cases/safety/ConstOverflow.ash`, `ConstIndex.ash`). Constant out-of-bounds indexes are only denied for `final` arrays: programs here demonstrate the run-time IndexOutOfBounds on plain locals.
- **`kiln` frees Strings** (static Linux builds). The lowering is shared with `ashvm` (`jl_drops` is now a mask: `ashvm` frees Strings, arrays and objects, `kiln` Strings only). When the IR contains `mem_free` / `mem_cat`, the driver turns on free lists (`codegen/C/runtime/heap.c`): one list per 16-byte size class up to 512 bytes, heads in a new 264-byte slot of the ELF globals (`KILN_FREELIST_ADDR`). Only the two places that make freeable Strings (concatenation, `str()`) use the new `heap_emit_alloc_str`, which rounds the request and pops a recycled block; the plain alloc routine used by arrays, maps and everything else is untouched, so those cost exactly what they did (an array-heavy loop measures the same with and without a free elsewhere in the program). `mem_free(x)` pushes a String block on its class list; `mem_cat(a, b, flags)` concatenates and frees the temporary operands. Programs that never free, Windows and `--link=shared` builds get the old allocator. `System.free` is now `mem_release`: `ashvm` frees, `kiln` ignores it (it cannot know where an arbitrary String came from). A loop of 3 million short-lived strings runs in 12 MB on `kiln` (249 MB with `memory-safety: off`). `tests/scripts/memory_check.sh` (both engines, 3 GB cap) checks this; the ownership tests also run on `kiln`.
- **`kiln` frees arrays too.** `new T[n]` (one dimension) compiles to the new `mem_newarr1` builtin with exactly `n` elements of capacity, array literals and the elements block go through the recyclable allocator when the program frees arrays (`mem_free_arr` in the IR), and `mem_free_arr(x)` puts the array object (32-byte class) and its element block (`capacity * 16` bytes, 16 for an empty one) on the free lists. Programs that never free an array keep the plain allocator. A churn loop of `new int[4]` runs 3.7x faster (0.0097 s vs 0.037 s for 400 thousand iterations, no page growth) and 300 thousand array iterations stay in 12 MB. Not freed: the blocks `push` abandons while an array grows, inner arrays of `new T[a][b]`, objects (maps) on `kiln`. The IR names are `mem_free` (Strings, objects), `mem_free_arr` (arrays; an alias of `mem_free` on `ashvm`), `mem_cat`, `mem_release`.
- **`kiln` frees objects too.** An instance of a plain class is a map built by one map literal with all its fields, so it never grows: `mem_free_obj(x)` puts its map object (32-byte class) and its entries block (`capacity * 32` bytes) on the free lists, and map literals go through the recyclable allocator when the program frees blocks. 300 thousand `new Point(..)` pairs run in 12 MB (105 MB with safety off); the whole `kiln` suite, including the ownership tests, passes with objects freed. The IR now names `mem_free` (Strings), `mem_free_arr`, `mem_free_obj` (aliases of `mem_free` on `ashvm`). Still leaked on `kiln`: the blocks `push` abandons, inner arrays of `new T[a][b]`, field contents.
- **Borrows are inferred for parameters.** A parameter of a project method or constructor that the body only reads (indexing, `.length`, operands, String methods returning primitives, print arguments, fields of a plain class, passing it on to another read-only parameter) is borrowed: passing a local to it neither moves the local nor stops it from being freed (`front/src/jown`, `param_borrowed`). Returning, storing, capturing in a lambda, passing to library code that may keep it, reassigning it from an alias, recursion, and calls through a parameter that may be a subclass all make the parameter escape, so the call moves its argument as before. The target must be fixed at compile time (static, private, final, constructor, or a class nothing extends). So `size(a); size(a);` is no longer a use-after-move, and `a` is still freed. Tests: `OwnBorrowInfer`, `OwnBorrowTricky` (aliasing traps; ASan-clean), `OwnMovedKeep`, `OwnMovedCall`.
- **Objects free the fields they own.** A String or array instance field of a plain class is *owned* when its initializer (if any) is fresh, every assignment anywhere in the project stores a fresh value (or `+=`), and every read is a benign one (index, `.length`, operand, String method returning a primitive, print argument, for-each) -- a getter, `a.f = b.f`, a lambda capture or passing the field on makes it shared (`front/src/jown`, `JField.own`; records are never owned). Freeing an object then frees its owned fields first (`mem_free(o["f"])`), and reassigning an owned field frees the old value (`label = label + n`). Reference fields default to `none`, which freeing ignores. Test: `OwnFreeFields.ash` (a shared literal field, a field assigned from a parameter and a field returned by a getter stay alive; ASan-clean, same output on `kiln`).
- **Lists are freed.** A local or an owned field of type `List` / `ArrayList` built by `new ArrayList<>()` (or returned fresh by a project method) is freed like an array when it is only used through `size`, `isEmpty`, `get`, `set`, `add(T)`, `remove(int)`, `removeLast`, `contains`, `sort` and for-each. `subList`, `stream`, `iterator`, `forEach`, `add(int, T)`, passing the list on, returning it from a getter or aliasing it keep it alive (`front/src/jown`, `list_type`, `list_method_ok`; the methods are the `@Lower` templates in ash-stdlib `ArrayList.ash`). Only the list's own storage is freed, never its elements. The IR uses `mem_free_arr` for lists. Test: `OwnFreeLists.ash`; the examples that use lists run with them freed (ASan-clean, `kiln` suite green). Maps/sets are not freed: their entries are separate chained arrays.
- **Maps and sets are freed on `ashvm`.** A local or an owned field of type `Map` / `HashMap` / `Set` / `HashSet` built by `new HashMap<>()` / `new HashSet<>()` is freed when it is only used through `size`, `isEmpty`, `put`, `get`, `containsKey`, `remove`, `keys`, `values`, `add`, `contains` and `toList` (the `@Lower` templates in ash-stdlib `HashMap.ash` / `HashSet.ash` / `Map.ash` / `Set.ash`; all of them build new lists or return elements, none hands out the container). New builtin `mem_free_map` frees the `[key, value, next]` entry chains the prelude builds, the map's own keys and its tables; keys and values the program stored are left alone. Parameters of list / map type that a method only reads are borrowed like the others. `kiln` does not free maps. Test: `OwnFreeMaps.ash`; 100 thousand iterations of a 3-entry map run in 12 MB (150 MB with safety off).
- **Less garbage and a faster `hashmap.ash`** (also with safety off, on both engines): the map prelude no longer builds the element-count key `chr(1) + "n"` on every operation (it is `__KP[2]`, built once), and `type()` returns static strings instead of a malloc'd copy on each call. `hashmap.ash` runs about 5% faster than the original commit; nothing else changed in speed.
- **`kiln` frees maps and sets.** `mem_free_map(x)` walks the map's entries, frees each prelude `[key, value, next]` entry array (object and element block, following the collision chain), then the map's entries block and the map object; keys and the program's values are left alone. Map growth (`maps_mutate`) allocates through the recyclable allocator when the program frees blocks and gives back the 16-byte block of an empty literal; blocks of non-empty maps that grow are kept (a loop may still hold them). The same decision as for arrays: `kiln`'s `push` is not made to free its old block, because `each` loops cache the element pointer and a free would change the behaviour of programs that append while iterating. 400 thousand iterations of a three-entry map run in 12 MB (same speed as without freeing); `OwnFreeMaps` and the examples that use maps pass on `kiln` with maps freed.
- **Differential fuzzing of the ownership pass** (`ashvm/tests/scripts/ownership_fuzz.sh` + `ownership_fuzz_gen.py`): random programs that mix Strings, arrays, lists, maps and objects with aliasing, moves, factories, keeping helpers, hand-outs of fields, containers, loops with `continue`/`break`, `try`/`catch`/`finally`, reassignment and recursion must print the same with `memory-safety` on and off (and stay AddressSanitizer-clean with `ASAN=` and match `kiln` with `KILN=1`). About 1,000 accepted programs on `ashvm` (plus 180 on `kiln`) ran clean; the move checker rejected roughly 8% of them, as intended. Nothing was found, which is the result to expect from the corpus tests above, not a proof.
- **`ashvm` frees the Strings inside lists and String arrays.** A candidate `List<String>` / `String[]` (local, or owned field) whose elements are all fresh concatenations (`xs.add("a" + i)`, `xs[i] = "b" + i`, `xs.set(i, "c" + i)`, `new String[n]`, `{"a" + i, ...}`) and whose elements are only read in harmless places (receiver of String methods returning primitives, print arguments, operands, for-each variables used the same way) gets `mem_free_elems(x)` before it is freed. An element stored from a literal or another variable, `get(i)` / `xs[i]` kept in a local or passed on, a ternary or lambda around a read, or a for-each variable that escapes switches it off for that container; `remove` / `set` hand back the element, which has left the container. Test: `OwnFreeElems.ash`; the fuzzer (`ownership_fuzz_gen.py`) gained element patterns (alias through a local, keep, ternary, loop variable, remove) and ran about 560 accepted programs clean under AddressSanitizer. `kiln` frees them too (next entry).
- **`kiln` frees the Strings inside lists and String arrays** (`mem_free_elems`: a loop over the array's elements that puts each String block back on its free list; the same analysis decides when). An eight-element list built 100 thousand times runs in 12 MB (82 MB with safety off). `ownership_fuzz.sh` with `KILN=1` compared about 470 more random programs on `kiln` against `ashvm`: identical. Benchmark note: relinking the same `ashvm` objects in two other orders moves single benchmarks by about 1.5% either way (this build is the fastest on `countdown`, the others tie), so the earlier 1% swings are link-layout noise; `vm/` is unchanged.
- **`kiln` frees on Windows too (static builds).** The free-list table moved to the OS-agnostic `runtime_layout.h` (`KILN_FREELIST_SIZE`) and got a slot in the PE globals (`KILN_PE_FREELIST_ADDR`), `heap_enable_free_lists` and the driver now accept any `--link=static` target, and the allocator code is the same on both OSes. Checked under the Unicorn emulator (`windows_emulated_check.sh`): 46 of 48 programs, including all the ownership tests with their frees, print exactly what the Linux build prints; the two that differ are `ProcFork` (Linux-only syscalls) and `FileIo` (the emulator's fake file system), the same two that differ without any freeing. `run_pe_emulated.py` had stopped working with the 4 GB heap reservation (its fake `VirtualAlloc` handed out addresses overlapping the image at 0x140000000); its heap now starts at 0x200000000. `--link=shared` builds still use the old allocator.
- **A loan may not be kept.** `&x` / `&mut x` handed to a project method or constructor whose target is known at compile time (static, private, final, constructor, or a class nothing extends) and that stores, returns or passes on that parameter is now an error: "cannot lend 'a' with '&': 'put' keeps this parameter; pass 'a' by move or clone it". This is Rust's rule that a borrow cannot outlive the call. `&` is new in this work, so no existing code is rejected. Calls whose target is not fixed (overridable or library code) still accept a loan, and the loaned variable is never freed. Test: `OwnLendKept.ash`. `OwnFreeFields` now moves its array into the constructor instead of lending it.
- A loop building 300 thousand to 3 million short-lived strings and arrays runs in 12 MB instead of 3.4 GB with output unchanged (`ashvm/tests/cases/ownership/OwnFree.ash`, `OwnFreeFlow.ash`; also run under AddressSanitizer). Benchmarks (`fib`, `loop`, `countdown`, `loop_varbound`, `hashmap`) are within noise of the pre-change binary; projects without the flag generate exactly the old IR.

## 2026-10-18 (frontend consolidation: hearth/front is the only frontend)
- **`ashvm` and `kiln` no longer have lexers, parsers or import systems of their own for Ash source.** Both link `libashfront.a` and call `jdriver_compile_file()` (`front/src/jdriver`): lex, parse, type-check, lower. The result is the internal IR, passed in memory to the `ashvm` compiler / `kiln` code generator. Deleted: `ashvm/src/lexer`, `kiln/src/lexer`, `@import` handling, import-path resolution, import aliases, circular/collision checks (`ashvm/src/compiler/*/stmt_import.*`, `*/import_paths.*`, `kiln/src/parser/*/imports`).
- **One IR lexer** (`front/src/ir`) replaces the two old lexers. The IR is one unit of top-level declarations whose `start` function the consumer calls; it has no `@import` and no user entry point. Old-syntax source is rejected by the front end with a message naming the replacement (D3).
- **`ashfront` is gone** (source, build target, `bin/ashfront`, docs). Its modes moved into the real tools: `ashvm run [--wrap-int] <file.ash>`, `ashvm check <file.ash>`, `kiln <file.ash> -o <out> [... --wrap-int]`. `--lower` and `--parse` were dropped (`ashvm check` parses and type-checks).
- **The `ashvm` REPL is Java-like**: imports, types, static methods and statements persist; a bare expression is printed. Each line runs in a child process on a replay of the accepted history (`front/src/jrepl`), so errors cannot corrupt the session. The old REPL and its VM recovery hooks (`vm_run_from`, `vm_set_repl_recovery`, `vm_repl_checkpoint`) were removed.
- **Performance**: `x = x OP (number|local);` now fuses into `OP_ACC_LOCAL` like `local x = x OP ...` did, and the lowering stops parenthesising assignment right-hand sides. On the same Java-like source this is faster than before (loop 2342 -> 1577 ms, countdown 2235 -> 1513, loop_varbound 2371 -> 1553; fib 252 -> 248, hashmap 299 -> 291). Migrated benchmarks `ashvm/benchmarks/*.ash` now match or beat the hand-written old-syntax numbers except `hashmap` (291 ms vs 116 ms for raw VM maps: Java `HashMap` is an equals/hashCode library over them, unchanged by this work) and a ~4 ms start-up for loading the reachable stdlib.
- **Tests**: the 144 old-syntax cases under `ashvm/tests/cases` and `kiln/tests/cases` were deleted (they exercised the old language and its builtins directly: `forge`/`attempt`/`raise` semantics, builtin error wording, `@import` resolution, GC stress on old programs); the behaviours that still exist are covered by `front/tests/cases/run` and `examples/`. `GcChurn` and `HeapGrowth` were migrated. `run_regression.sh` in both projects compares every program with its `.out`; `gc_check.sh`, the Windows emulation/Wine checks and `shared_link_check.sh` now iterate over the shared programs. The two Pyre benchmark programs were migrated.
- Not carried over: the `matrix_mul` builtin has no new-Ash API, so it is unreachable from Ash (the builtin is still present in the IR layer of both engines).

## 2026-10-17 (collector: layout-noise floor measured)
- Two collector-free builds of the same source differing only in `-falign-functions=64` differ by up to 0.7% on the baseline benchmarks (ratios 1.000, 0.993, 1.000, 0.998, 1.000); the collector build measures 1.007, 1.004, 1.002, 1.003, 0.995 against the same base. ## 2026-10-08 (pyre: the GPU is real now -- one loss, one 34x win, and the dispatcher gap that exposes)
Follow-up to the kiln-integration entry below, same day: this sandbox turns out to be WSL2 on the user's actual machine, which has GPU passthrough infrastructure (`/dev/dxg`, Microsoft's D3D12 translation libraries) already present but no Vulkan driver installed. Installing `vulkan-dzn` (Mesa's Vulkan-over-D3D12 driver) plus `mesa` made `vulkaninfo` and `ash_gpu_detect()` both find the real **AMD Radeon RX 9070 XT** ("Microsoft Direct3D12 (AMD Radeon RX 9070 XT)", driver `DRIVER_ID_MESA_DOZEN`, `shaderFloat64 = true`) -- the Vulkan path written two entries ago has now actually run, for the first time ever.

**`matrix_multiply` on the real GPU: a loss.** Same-moment forced-CPU-vs-real-GPU measurement: CPU backend 0.44s, GPU backend 1.07-1.11s -- about 2.5x *slower*. Matches the caveat already written into that shader's comments before ever running it: fp64 throughput on a consumer GPU is a fraction of fp32, the shader is deliberately untiled (one thread per output element), memory is host-visible/host-coherent rather than device-local, and Dozen is explicitly a translation layer ("not a conformant Vulkan implementation, testing use only" -- Mesa's own warning), not a native driver.

**So: is there any workload shape this GPU setup actually wins on?** Added `ash_gpu_chaos_iterate` (`pyre/src/H/runtime/ash_gpu.h`, CPU backend `src/C/backends/cpu/chaos.c`, Vulkan backend `src/C/backends/vulkan/chaos.cpp` + `src/shaders/chaos.comp`) specifically to answer that: 2 million independent elements, each iterated 4000 times through `x = sqrt(abs(x)+1)*0.99999+0.00001` in place -- the opposite shape from matmul, huge compute per element, trivial data movement, no cross-element dependency, no tiling to get right. (The recurrence uses `sqrt`/`abs` rather than `sin`/`cos` because GLSL's `GL_ARB_gpu_shader_fp64` extension turns out to add `double` overloads for the former but not the latter -- `glslc` flatly rejected `sin(double)` -- found by trying it, another thing that can't be learned from documentation alone.) New `pyre/benchmarks/chaos/run_benchmark.c` runs both backends back to back in one process for a fair same-run comparison and cross-checks their results. Result: CPU ~14.5s, GPU ~0.43s -- **~34x faster**, with `max |CPU - GPU| = 0` (bit-identical results across all 2M elements, not just "close").

**The real finding isn't either number -- it's that nothing currently tells them apart.** Both dispatchers in `src/C/runtime/device.c` unconditionally prefer GPU-when-available with no cost model at all, which the matmul result proves is actively the wrong call for that kernel today. Building the actual "which workloads go on the GPU" algorithm is explicitly **not done now** -- the user asked for it to wait until everything else is wrapped up -- but it's written down as the clear next task in `pyre/todo/todo.md`'s new "Smart dispatch" section, with these two real, measured, contrasting data points as the calibration targets for whoever builds it.

## 2026-10-08 (kiln: real Phase 4 integration -- matrix_mul calls into libashgpu.so under --link=shared)
Follow-up to the ashvm/Vulkan entry below, same day: kiln gets the matching half of "ashvm and kiln actually use Pyre" (ideas/assigned.md), and finishes "Kiln integration" from ideas/gpu_acceleration.md's own phase table ("Kiln emits calls to ash-gpu for suitable workloads") for real -- a GOT call into `libashgpu.so`, not a native reimplementation of the algorithm, which is the distinction that phase is actually about.

**Why `--link=shared` only:** kiln's default output is a hand-rolled, zero-dependency ELF/PE binary (AGENTS.md's "no external dependencies" is kiln's whole reason to exist). Pyre's CPU backend needs OpenMP and `dlopen`. `matrix_mul(a, b)` (new builtin, `kiln/src/codegen/C/collections/matrix_mul.c`) is therefore available only under `--link=shared`; under the default `--link=static` it's a clear compile error naming why, never a silent dependency added to every compiled program.

**The mechanism:** `--link=shared` already dynamically links ONE needed library (`libkilnrt.so`) via a real `PT_INTERP`/`ld.so` setup (`elf/C/elf_dynamic.c`). Extended it to declare `libashgpu.so` as a SECOND needed library -- one more `DT_NEEDED`, and `ash_gpu_matrix_multiply` folded into the SAME combined hash/dynsym/GOT/rela table as kiln's own runtime imports (`KILN_DYN_TOTAL_IMPORTS` = `RUNTIME_IMPORT_COUNT_` + the new `AshGpuImport` enum's count, `elf/H/elf_dynamic.h`) rather than a second parallel set of tables, since `ld.so` resolves a symbol name against every needed library regardless of which table region declared it. New `codegen/C/platform/linux_call.c`/`.h` add the one piece kiln never needed before: a SysV ABI call wrapper that dynamically 16-byte-aligns RSP before the call (reusing `win_call.c`'s existing scratch slot, since a target is always Linux or Windows, never both) -- kiln's own hand-rolled routines never needed this because none of them use an alignment-sensitive instruction, but a real gcc/g++-compiled function with OpenMP and SSE/AVX does. `matrix_mul` itself (square arrays-of-arrays of numbers, same N, matching `ash_gpu_matrix_multiply`'s own signature) flattens both arguments into temporary flat buffers, calls through the GOT slot, and unflattens the result -- the bridge todo.md 2.A's still-nonexistent `Buffer`/`Tensor` type would otherwise be. Pyre's own `pyre/Makefile` gained a `lib/libashgpu.so` target and an `install` target (writes to kiln's hardcoded `KILN_RPATH`, same spot `libkilnrt.so` already installs to).

**Verification, in both directions:** `kiln/tests/scripts/shared_link_check.sh` (new -- `--link=shared` had zero automated coverage before this) compiles a sample of ordinary tests under both link modes and diffs them, confirming the second `DT_NEEDED` and the bigger combined table didn't disturb kiln's own existing runtime imports; `run_regression.sh` (default `--link=static`) stayed byte-identical throughout. Separately, actually running `matrix_mul` (not just compiling it) surfaced a real, previously-invisible kiln bug: its process-exit path used the `exit` syscall (60, terminates only the calling thread) instead of `exit_group` (231, terminates every thread in the process) -- invisible for the entirety of kiln's prior history because no kiln program had ever spawned a second thread, until `ash_gpu_matrix_multiply`'s OpenMP worker pool did. The symptom was exact and confusing: the program printed its correct answer and then hung forever, waiting on orphaned worker threads the exited main thread left behind. Fixed in all three exit sites (`codegen/C/runtime/print_int.c`'s `codegen_exit0`, `codegen/C/builtins/exit_builtin.c`, `codegen/C/runtime/errors.c`'s two uncaught-error paths) -- `exit_group` with a single thread behaves identically to `exit`, confirmed by every existing test's output staying byte-for-byte unchanged. This is the entire point of running something instead of stopping at "it compiles" -- see the previous entry's Vulkan backend for the still-outstanding counterexample.

`ideas/assigned.md` and `pyre/todo/todo.md` updated accordingly: both ashvm and kiln now genuinely call into Pyre "when it's ok to" (ashvm: always, once `N >= ASH_GPU_MIN_N`; kiln: always under `--link=shared`, never under the zero-dependency default).

## 2026-10-08 (kiln: dynamic heap, chained index assignment -- pyre prerequisites)
First item off `pyre/todo/todo.md` (prerequisites before building the `ash-gpu` compute backend, "Pyre"). Both changes are `kiln`-only; `ashvm` regression suite re-checked and unaffected.

**Dynamic heap, no more fixed 16MB cap:** `kiln`'s bump allocator grabbed one fixed-size arena at startup (`brk` on Linux, one `VirtualAlloc` on Windows) and silently segfaulted the moment a program allocated past it -- a 500x500 matrix of temporaries, or any sufficiently long-running loop, would crash with no runtime error at all. Now it grows in 64MB chunks as needed: a new `heap_limit` globals slot (right after `heap_ptr`, pushing `try_depth`/handler-stack/argv/modstate addresses down by 8 bytes on all three executable layouts -- static ELF, PE, and `--link=shared`'s dynamic ELF) tracks the current committed boundary, and the alloc routine calls `brk` again (Linux) or commits the next chunk of an upfront 4GB `MEM_RESERVE` (Windows, since `VirtualAlloc` has no brk-style "extend in place") whenever the bump pointer would cross it, rounding the request up to a whole chunk so one oversized allocation still succeeds in a single grow step. The ~27 existing `heap_emit_alloc` call sites are unaffected: the growth path preserves the exact same clobber set (RBX/RCX/RDX/RBP/RSP untouched) via push/pop around the one-off syscall/API call. New `tests/cases/memory/heap_growth.ash` leaks 2,000,000 small arrays (confirmed to segfault the old binary, confirmed correct under the new one).

**`C[i][j] = val` (chained index assignment):** previously only `IDENT[index] = expr` parsed; a second `[` after the first `]` was a parse error, forcing the manual `local row = C[i]; row[j] = val; C[i] = row;` workaround. `index_assignment_statement` (`parser/C/core/parser.c`) now loops on `[index]` and reads through every level but the last via `codegen_index_read` (promoted from `expr.c`-local `emit_index_read` to a shared declaration in `expr.h`, the same primitive `postfix()` already chained reads with) -- only the final index is a store, into whatever object the reads produced (arrays are reference values here, so there is nothing to write back to the outer container). A string anywhere in the chain, including the final target, still raises the existing `cannot assign to a string index`. `tests/cases/collections/chained_index_assign.ash` covers two and three levels deep, a matrix-accumulation shape, a mixed array/map chain, and the string-immutability case.

**Also added, not yet wired to anything:** `heap_emit_checkpoint`/`heap_emit_reset` (`codegen/C/runtime/heap.c`), an arena-style rewind-the-bump-pointer pair for Pyre's own future lowering to reclaim short-lived loop-body scratch without an OS call. Deliberately *not* hooked into general `each`/`during` loop bodies: doing that soundly needs an escape analysis (does any value allocated in the loop body outlive the iteration -- outer-scope write, closure capture, return/yield, a retaining function call) that kiln's single-pass compiler doesn't have and goals.md item 1 defers for exactly that reason; an unsound version would silently corrupt memory instead of just leaking it, which is worse than not having the feature. Verified directly against a hand-built tiny ELF (bypassing the Ash front end, since there is no surface syntax for it yet): allocate, write, reset, allocate again, and confirm the second allocation reuses the first's exact address.

Not a goals.md item: goal 1 (Rust-grade memory safety, an off switch, bounded memory) is a different, much larger deliverable -- this only removes a hard crash, it does not bound memory or free anything.

## 2026-10-08 (the rest of the language gaps ash-json found)
Second batch; the numbers in parentheses are the entries of ash-json's list of language gaps. Every change is on both `ashvm` and `kiln` with a test in each `tests/cases/` tree, and the regression diffs below were checked against a baseline built from the previous commit (the intended ones: booleans printing as `yes`/`no`, insertion-ordered maps, the new number format, unified error wording). As before, there is deliberately no `remove` builtin (ash-json defines its own `remove` functions, and a builtin name would shadow them); `delete(array, i)` covers it.

**Booleans (4):** new value type. `yes`/`no`, comparisons, `not`, `and`/`or`, `has`, `file_exists`, `contains`/`starts_with`/`ends_with`, `rename_file`/`delete_file`/`make_dir` and `write_file`/`append_file` produce it. Prints `yes`/`no`, `type()` is `"boolean"`, `str(yes)` is `"yes"`, `yes == 1` is false (arithmetic and truthiness still treat it as 1/0). `ashvm`: `VM_BOOL`, `vm_values_equal()` (also gives arrays/maps/functions identity equality, as kiln already did). `kiln`: `TAG_BOOL`. Conditions on both engines now accept booleans, numbers and `none` and raise `invalid operand type in condition` for a string/array/map/function (kiln used to treat a map as truthy; `kiln` has one `codegen_pop_and_test_truthy` instead of three copies). `filter` accepts a boolean-returning predicate.

**Insertion-ordered maps (3):** `ashvm`'s open-addressing table became a dense entry list plus an index (deleting no longer leaves probe-chain holes, which also fixed lookups after a delete); `kiln`'s `delete` shifts later entries down instead of swapping in the last one. `keys`/`values`/printing agree on both.

**Number format (8):** one format for both engines. `ashvm` used `%lld`/`%g` (6 significant digits), `kiln` printed 6 fraction digits and produced garbage past int64. Now: integers plainly below 1e15, otherwise up to 6 fraction digits with trailing zeros dropped, and scientific (`1e+21`, `1.5e-07`) at or above 1e15 / below 1e-6; `nan`/`inf`/`-inf`. `kiln`: `codegen/C/runtime/number_format.c`, shared by `say` and `str` (it replaces two copies and also fixes a carry bug at `x.9999999`); `ashvm`: `vm_format_number`. 6 fraction digits is not shortest-round-trip; that stays a documented limit.

**`var.field` and `e.message` (9):** `x.name` on a local variable is `x["name"]`; indexing a string with a string yields the string itself, so `handle (e) { say e.message; }` works for built-in errors (strings) and raised maps alike on both engines.

**Error wording and structured errors (9):** caught messages are identical on both engines and carry no prefix or detail (`index out of bounds`, `key not found`, `invalid operand type in '+'`, `could not open file`, ...); `kiln` adds `error: ` itself when an error is uncaught. `raise` takes any value (`kiln`'s raise routine now carries the value's tag), so `raise {"kind": "parse", "line": 3}` is caught as a map. Built-in errors remain strings (making every caught error a map would break `"x: " + e`); `ashvm` also gained string indexing `s[i]` to match `kiln`.

**Sort (6):** `sort(array)` / `sort(array, cmp)`, in place, stable, returns the array; `cmp(a, b) > 0` means `a` goes after `b`. `ashvm`: merge sort; `kiln`: insertion sort (O(n^2)).

**Files (17):** `rename_file`, `delete_file`, `make_dir`, `list_dir` (names without `.`/`..`, directory order). Windows `kiln` targets get real `MoveFileA`/`DeleteFileA`/`CreateDirectoryA` imports, and `list_dir` walks `FindFirstFileA`/`FindNextFileA`/`FindClose` (shared with the Linux path through `emit_add_entry`). The Windows code is verified by running it: `kiln/tests/scripts/windows_emulated_check.sh` executes each test case's PE under the Unicorn emulator with a Python stand-in for kernel32 (real files underneath), and all 63 runnable cases match their Linux builds, `fs_ops` included. The same cases also match under Wine 11.19 (`windows_wine_check.sh`), including `C:\\` paths for the file operations, which removes the dependence on my own kernel32 stand-in. Neither is real Windows.

**Strings (18, 19):** `contains`, `starts_with`, `ends_with`, `repeat`. Complexity, as requested: strings carry their length now on `ashvm` (`len`, `substring`, `s[i]` no longer `strlen`), and are length-prefixed on `kiln`, so `len`/`s[i]` are O(1) and `substring` O(piece). `s += x` copies the whole string (quadratic over a loop, and nothing is freed); `join(parts, "")` is the linear builder. `kiln`'s `push` grew arrays by 4 slots per reallocation (quadratic memory against its 16 MB bump heap, so a 200k-element array crashed); it doubles now.

**Builtins as values (11):** `type(len)`, `map(xs, str)`, `local f = len;` compile a one-line wrapper lambda by re-lexing a synthesized `forge (a0, ...) { yield name(a0, ...); }`. Variadic builtins (`sort`) wrap with their minimum arity.

**Forward declarations (13):** a pre-pass over each file reserves every named `forge name(params)` (with its arity), so calls can precede the definition and functions can call each other. `ashvm`: `compiler/C/prescan.c`; `kiln`: calls to a not-yet-defined function emit a placeholder that is patched when the body is compiled (`function_add_call_fixup`/`function_resolve_fixups`). A reserved name that is never defined is `undefined function`. A local variable now shadows a function of the same name on `ashvm` too (kiln already did).

**Imports (14, 15, 16):** `@import <file.ash> as name;` chooses the namespace. Transitive imports are now documented (README) and covered by `imports_transitive_test`. Every top-level `local` of an imported file is a module-level variable: its expression runs once where the `@import` is, the file's functions read it and update it (`NAME = ...;`, `NAME += ...;`, `NAME++;`, `NAME[i] = ...;`), and `file.NAME` reads it from outside. `ashvm`: `OP_GET_GLOBAL`/`OP_SET_GLOBAL` (256 slots); `kiln`: a 128-slot table in the globals region of every binary (+2 KB). It replaces the old "literal number/string constant only" rule (such constants were read-only).

**Smaller (7, 10, 12, 20, 21):** exponent literals and `num("1.5e2")` already landed in the first batch; `exit(code)` ends the program with a status (an uncaught error exits 1), which is what a test runner needs; the `kiln` output that "silently stopped" after `attempt { delete(array, 0); ... }` came from `delete` treating an array as a map and is gone now that `delete(array, i)` exists (`attempt_array_delete` covers it).

**Not done:** nothing left from that list.

## 2026-10-08 (language gaps found by ash-json: function limit, `attempt` unwinding, short-circuit, string order, `chr`/`ord`, array mutation, more)
First batch from the ash-json 0.2.0 needs list (numbers are the entries of ash-json's list of language gaps). Everything below behaves the same on `ashvm` and `kiln` and has a test in both `tests/cases/` trees.

**Function limit (0):** `MAX_VM_FUNCS` / `MAX_KILN_FUNCS` 64 -> 1024, so `@import <ash-json>;` (87 functions) loads.

## 2026-10-07 (three more parity bugs, found verifying the JSON module before handing it off)
Before writing `mission.md` (a hand-off doc for shipping the first real `forgepack` module — a JSON codec in pure Ash), actually ran the module's code through both engines rather than just writing it and hoping. Found three more real bugs this way, on top of `type()` above — the module itself was the test case the existing regression suites never exercised (real, non-trivial, deeply-nested-and-recursive user code, not hand-picked feature probes).

**Bare reassignment (`x = expr;`, no `local`) didn't exist on `ashvm` at all.** A known, previously-*documented*-but-never-fixed gap from an earlier session (flagged when asked "are both engines exactly the same" — the honest answer was no, citing this exact example) — writing a parser that reassigns a position variable throughout (`i = json_skip_ws(s, i);`) finally made it a hard blocker instead of a noted gap. `identifier_statement()` (`compiler/C/stmt.c`) handled a call, an index-assign, compound-assignment, and `++`/`--` on an already-declared variable, but fell through to "unexpected identifier statement" for a plain `=`. `kiln` already supported this (`assignment_statement()` always reassigns an existing slot). Fixed by adding the missing case: `OP_SET_LOCAL` after a full `expression()`, same as `local_statement()`'s own "already declared" path.

**A namespaced call used as its own statement didn't parse on either engine.** `json.save(path, value);` (the entire point of a `save()` function — call it for the side effect, don't use its result) failed on both: `ashvm` with "unexpected identifier statement", `kiln` with "expected '=' after variable name". `module.func(...)` as part of an *expression* (`local x = json.load(...);`) already worked (`expr.c`'s `primary()` has a `TOKEN_DOT` case) — the gap was specifically the bare-statement entry points (`identifier_statement()` on `ashvm`, `assignment_statement()` on `kiln`), which checked for a plain call, an index-assign, etc., but never checked for `TOKEN_DOT` before falling through. Fixed by mirroring the exact dotted-call logic from each engine's own expression parser, with a trailing `OP_POP`/pop-pop to discard the unused return value, matching how a bare non-namespaced call statement already does.

**Import compiler rejected any `local` inside an imported function's own loop.** `try_declare_import_constant()` (the mechanism that lets a top-level `local NAME = <literal>;` in an imported file become a namespaced compile-time constant, e.g. `mathlib.PI`) was called unconditionally for *every* `local` statement anywhere in an imported file's compiled body — including deep inside one of that file's own functions, since the "currently compiling an imported file" flag is set once for the whole file, not scoped by block depth. Every `local` inside `json_skip_ws`'s loop (`local c = substring(s, i, i + 1);`) got misdiagnosed as a failed attempt at a top-level namespaced constant ("imported top-level 'local' must be a literal number or string constant") even though it's three blocks deep, nowhere near the file's top level. The sibling guard in `statement()` already correctly checks `block_depth == 0` for the analogous "only forge/local allowed at top level" restriction — this specific call site just never got the same check. One-line fix, mirrored on both engines.

All three fixes verified together: the full JSON module (parse/stringify/load/save, nested arrays-of-objects-of-arrays, malformed-input error handling via `attempt`/`handle`) now runs byte-for-byte identical on both engines, including a fourth bug that was in the *module's own code*, not the engines — `json_parse_string`'s loop had no end-of-input check (`during yes` with only "found a closing quote" as the exit condition), so an unterminated string in malformed input scanned forever: OOM-killed on `ashvm`, segfaulted on `kiln` (its bump allocator has no bounds check once the arena's exhausted). Fixed in the module, not the engines — bounded the loop on `i < len(s)` and `raise` on falling through.

## 2026-10-07 (`type()` builtin, both engines)
A genuine gap found while designing the first real `forgepack` module (a JSON library): there was no way for pure Ash code to ask a value what it *is*. Every existing builtin either requires a specific type already (`keys()`/`has()` error on a non-map, `upper()` on a non-string, ...) or works the same way regardless of type (`len()`). A general `json.stringify(value)` has to decide "format this as an array vs. a map vs. a string vs. a number" from an arbitrary value with no static type — there's no way to do that without some form of runtime introspection.

Added `type(value)` → `"number"/"string"/"array"/"map"/"function"/"none"` to both engines. `ashvm`: builtin id 27 (`builtins/C/core.c`, `builtins/C/builtins.c`), a straight switch on `VMValue.type`. `kiln`: a new module (`codegen/C/builtins/type_builtin.c`) — pop the value's tag, branch, and push one of six pre-embedded string literals via the already-existing `codegen_string_literal_bytes()` (the exact same length-prefix-embedding helper regular string literals use, so the result is a completely ordinary string value, not a special case). `ashvm`'s own print path distinguishes `"<function>"` vs. `"<closure>"` (see the array/map-printing fix further down this file), but `kiln` has no separate closure tag at all to match that with — `type()` collapses both to `"function"` on `ashvm` too, so the two engines agree on every possible result, rather than exposing a distinction only one side can make.

## 2026-10-07 (four cross-engine parity bugs, found by a side-by-side audit)
Ran the same `.ash` source files through both engines and diffed stdout byte-for-byte, which the previous entry's feature-parity work made possible for the first time (no point diffing output that couldn't even be compared before). Found four real bugs — three in `kiln`, one `ashvm`-only — fixed all four, then re-ran the audit to confirm convergence. The only remaining difference across every test file is map iteration order (`keys(m)`/`values(m)`), which is a documented, pre-existing architectural difference (`ashvm`'s real hash table vs. kiln's dense insertion-ordered array, see `codegen/H/emit/value.h`) and not a bug — neither engine's map iteration order was ever a language guarantee.

**`kiln`: missing `%` operator.** `TOKEN_PERCENT` was lexed but `term()` in `codegen/C/expressions/expr.c` only handled `*`/`/` — every `kiln` test needing modulo worked around it with `x - floor(x / n) * n`, which is a *different* operation for negative operands (floor-based mod vs. truncate-based `fmod`). Implemented as `a - trunc(a / b) * b` using the SSE2 primitives `floor()`'s codegen already established the pattern for (`emit_cvttsd2si` truncates toward zero directly, no separate correction step needed the way `floor()`'s overshoot-fix does) — matches `ashvm`'s C `fmod()` exactly, including sign: `-7 % 3 == -1`, not `2`. Verified identical output on both engines across positive, negative, and fractional operands.

**`kiln`: `say`-ing an array or map directly crashed or printed garbage.** `codegen/C/runtime/print_int.c`'s single print routine only ever had cases for `TAG_STRING` and `TAG_NIL`; anything else (including `TAG_ARRAY`/`TAG_MAP`, and, it turns out, `TAG_FUNCTION`) silently fell into the number-formatting path and tried to print a heap pointer as a double. This is why `kiln`'s own test suite never caught it: every test that uses `map()`/`filter()`/`keys()`/etc. immediately indexes into the result rather than printing it directly. Fixed with a new recursive printer (`emit_print_recursive_routine`, self-`call`s for nested arrays/maps, quotes string elements the way `ashvm`'s `vm_print_value()` does, falls back to `<function>` for anything else) plus a `number_routine` extracted out of the old inline digit-building code so both the recursive printer and the top-level routine can share it without duplicating ~90 lines of SSE2 asm. Wrote and threw away three register-clobbering bugs getting this right — hand-rolled x86-64 means `write_one_char()` (every bracket, comma, quote) clobbers RAX/RCX/RDX/RSI as a side effect of its own `write(2)`/`WriteFile` call, so anything that needs to survive across one has to live in memory (this routine's own `push rbp`-anchored frame, `[RBP-8/-16/-24/-32]`, *not* `[RSP+disp]`, which this codegen layer can't even encode — `RSP` as a base needs a SIB byte `modrm_mem_disp32()` doesn't emit), never in a register held "across" the call. Found via `gdb` on the raw statically-linked ELF (no section headers, no symbols — breakpoints by address, registers read at the exact instruction before/after a suspect load) after the first version printed `[1, ]` for `[1, 2]` instead of `[1, 2]`: traced to the loop's "index + 1, maybe print a comma, then store the new index" sequence holding the incremented index in `RCX` across the two `write_one_char(',')`/`write_one_char(' ')` calls that immediately clobber it.

**`kiln`: `len()` on a string read garbage.** `codegen_builtin_len()` in `codegen/C/collections/arrays.c` unconditionally read offset `+8` as "the count" — correct for `TAG_ARRAY`/`TAG_MAP` (they share the same `[capacity][count][data/entries_ptr]` object shape), but a string's length lives at offset `-8` from its payload (the length prefix that precedes the raw bytes), not `+8`. `len("hello")` was reading whatever garbage byte happened to sit 8 bytes into the string's own content. Fixed by branching on `TAG_STRING` first.

**`ashvm`: a fresh `local` declared inside a re-executed block (a `during`/`each` body, or a `given`/`otherwise` branch nested inside one) leaked a stack slot every pass instead of being replaced.** `ashvm` has no explicit "store a local" instruction — declaring one just means "whatever's on top of the stack now has this name," at a compile-time-fixed slot index (`frame->slots[n]`). `each`'s own three setup slots (array/index/var) already got cleaned up once, after the whole loop exits — but nothing cleaned up locals the *body* itself declared, every single iteration, and `given`/`during` didn't clean up after themselves at all. First iteration of `local x = i * 10; say x;` inside a `during` loop pushes `x` correctly; every iteration after that pushes *another* copy on top without popping the old one, while the compiled `OP_GET_LOCAL` for `x` keeps reading the same fixed slot index — the first iteration's value, frozen forever. `kiln` doesn't have this bug (confirmed directly, contradicting an assumption in the previous entry that this was some shared/inherited limitation): its locals are fixed `rbp`-relative memory addresses, not stack positions, so re-declaring one just overwrites the same address.

Fixed with a new VM instruction, `OP_TRUNC_LOCALS n` (`stack_top = frame->slots + n`) — an *absolute* reset, not a fixed number of `OP_POP`s, because a block can exit early (`next`, or one branch of a nested `given`) having declared fewer locals than its "normal" path does, so only the known target depth is ever safe to assume. `compile_given_stmt`/`compile_during_stmt`/`compile_each_stmt` each save `local_count` before their re-executed block, then call a shared `truncate_block_locals()` right where `next` already lands (before the per-iteration advance, so both the normal fallthrough and an early `next` converge on the same cleanup) — compiled to nothing extra when a block doesn't declare any locals of its own, so the common case (most loop bodies) costs zero bytes and zero instructions beyond what was already there. Verified against `fib.ash`/`loop.ash` (unaffected — this machine's own baseline for both, checked against the pre-session commit with a throwaway `git worktree`, already sits well above `AGENTS.md`'s reference numbers, which are from different hardware) and against deliberately adversarial cases (nested `given`/`next` inside `during`, nested `each` inside `each`) diffed byte-for-byte against `kiln`.

## 2026-10-07 (bring `ashvm` to the same feature level as `kiln`)
The reverse direction of the earlier kiln-parity work: `kiln` had six capabilities `ashvm` didn't (`stop`/`next` loop control, `raise` with a runtime string message, compound assignment, `++`/`--`, a ternary, and bitwise operators), plus `yes`/`no`/`none` literals from the same-day rename work. All ported, staying entirely within `ashvm`'s own execution model (interpreted bytecode VM, not compiled to native code like kiln) — this is language-feature parity, not architecture parity.

**`none` (nil) — the one real new concept, not just a port.** `ashvm`'s value representation had no null type at all (`VMType` was `{VM_NUM, VM_STR, VM_ARRAY, VM_MAP, VM_FUNCTION, VM_CLOSURE}`). Added `VM_NIL` and `vm_nil()` to `value/H/value.h`+`value/C/value.c`, then threaded it through every place a value's type is inspected: `truthy()` in `vm/C/errors.c` now treats `none` as always-falsy without erroring (matching kiln's "nil's payload is always exactly 0" rule) instead of the default "non-number errors" path every other truthiness check still takes; `do_EQ`/`do_NEQ`/`do_CMP_JUMP`'s equality branch in `vm/C/dispatch.c` gained a `VM_NIL == VM_NIL` case (including the fused-comparison path, which can reach it since `x == y` where both are locals holding `none` at runtime is a fusable `identifier CMP identifier` shape even though `x == none` itself never fuses — `none` is a keyword, not a number or identifier); `vm_print_value()` prints `none`. No existing builtin needed a change — `len()`, `str()`, etc. already reject unexpected types generically, so `none` just became one more value their existing type checks correctly refuse.

**`stop`/`next`** — a new `compiler/C/loop_stack.c`+`H/loop_stack.h` module (mirrors kiln's `parser/C/statements/loop_stack.c`), forward-jump bookkeeping per nesting level, no new VM instructions (reuses the existing `OP_JUMP`). Wired into `compile_during_stmt`/`compile_each_stmt` (`loop_push()` before the body, `loop_patch_nexts()` right before the per-iteration advance step, `loop_pop_and_patch_stops()` after) and `compile_forge_decl`/`lambda_literal` (save/reset/restore the loop-nesting depth around a function/lambda body, so `stop`/`next` inside one can't reach an enclosing loop it's textually written inside — ashvm's functions get their own `Chunk`, so a cross-chunk jump offset would be nonsense bytecode anyway; this turns that into a clean compile error instead). One genuine ordering subtlety for `each`: `stop` jumps and the loop's own condition-false exit both have to land at the *exact* same bytecode position (right before the each-loop's three cleanup `OP_POP`s, not after) so both paths fall through into the same cleanup — tested explicitly with nested `each` loops to confirm `stop` only breaks the innermost one and the stack stays balanced either way.

**`raise`** — needed a new opcode (`OP_RAISE`) and a new VM entry point (`vm_raise_value()` in `vm/C/errors.c`), since every existing runtime error goes through a fixed-size `char error_message[512]` buffer (fine for compile-time format strings, not for an arbitrary-length runtime string value). Added `raised_value`/`has_raised_value` globals (`vm/H/state.h`) that `vm_raise_value()` sets right before unwinding and `do_TRY_PUSH`'s recovery branch checks first, falling back to the `error_message` copy path for every other kind of error — so a caught `raise` hands back the exact raised string, not a truncated-at-512-bytes copy.

**Compound assignment / `++`/`--`** — deliberately *not* using the existing `OP_ACC_LOCAL` fused op (that only accepts a number-or-local operand, not a general expression — `x += f() + 1;` needs the full `GET_LOCAL, expression(), <op>, SET_LOCAL` path). `+=` reuses `OP_ADD` directly (same tag-aware string-concat-or-numeric-add logic `+` itself has); `-= *= /=` are number-only, same as `- * /` themselves. Unlike `ashvm`'s existing `local x = expr;` (which doubles as declare-or-reassign), these require the variable to already exist — `resolve_local_or_error()` added for the clean "undefined variable" diagnostic.

**Ternary and bitwise** — ternary sits at the bottom of `expr.c`'s precedence chain (above `logical_or`, matching kiln's placement), same jump-patch shape `given` already uses. Bitwise is one flat precedence level between `comparison` and `logical_and` (not real C precedence — a deliberate simplification kiln made first, carried over for consistency). Bitwise genuinely needed six new opcodes (`OP_BAND/BOR/BXOR/BNOT/SHL/SHR`) — real VM additions, but zero per-existing-instruction cost: computed-goto dispatch is a jump through a pointer array indexed by opcode byte, so adding table entries doesn't slow down dispatching to any *other* opcode. Confirmed by benchmarks below, not just asserted.

**A real, separate bug found and fixed along the way, not part of the language work:** `ashvm`'s Makefile had no `-MMD` header-dependency tracking (`AGENTS.md` explicitly documented this as a known fact: "`ashvm` has no `D/` tree"). Adding six new tokens to `lexer.h` shifted every subsequent `TokenType` enum value by 6 — `lexer.c` got recompiled (it was edited directly), but `stmt_import.c` (which only includes `lexer.h` transitively and wasn't itself touched) didn't, so it kept checking `TOKEN_LESS` against its *old* numeric value while the lexer now emitted the *new* one. Every `@import` in the regression suite broke with a confusing "expected '<' after '@import'" pointing straight at a literal `<` character. Root-caused by writing a tiny standalone program linked against just the lexer object file to print raw token type numbers, confirming the lexer was correct and the mismatch was elsewhere — then recognizing the "its Makefile makes no dependency files" line in `AGENTS.md` as the actual cause. Fixed by porting kiln's exact `-MMD -MP` Makefile pattern to `ashvm` (kiln's own Makefile comment already named this exact failure mode as the reason it has the pattern at all) — new `D/` trees added (seven subsystems, matching the existing `O/` trees), `AGENTS.md` and `README.md` updated since both explicitly documented "ashvm has no D/" as fact. Verified the fix actually works, not just that the symptom went away: touching `lexer.h` with nothing else changed now correctly recompiles all 10 dependent files, confirmed by counting recompiled files before and after.

Added regression tests: `tests/cases/basics/literals_test.ash` (`yes`/`no`/`none`, truthiness, equality, containers), `tests/cases/basics/operators_test.ash` (compound assignment, `++`/`--`, ternary, bitwise), `tests/cases/control_flow/loop_control_test.ash` (`stop`/`next`, including nested loops), `tests/cases/errors/raise_test.ash` (`raise`/`attempt`/`handle` with dynamic messages). `basics/` is a new feature folder — one of `AGENTS.md`'s own suggested names, previously unused in `ashvm`.

## 2026-07-21 (modules/imports + library storage, both engines)
kiln and ashvm both now support `@import <./relative/path.ash>;` and `@import <libname>;` (the latter resolving to `ash.libs/<libname>/<libname>.ash`), with imported functions and constants accessed via namespaced `ns.func(...)`/`ns.CONST` syntax. Implementation is source-level recursive merge, matching the design spec's Approach A: no linker, no new object format — the parser recursively parses an imported file's `fn` declarations and literal top-level `let` constants inline and registers them under a namespaced name (e.g. `"math.add"`) in the same flat function/constant tables everything else already uses. Verified by a real regression suite on both engines: `kiln/tests/imports_basic.ash`, `imports_lib.ash`, `imports_const.ash`, `imports_diamond.ash`, `imports_circular_check.sh`, `imports_collision_check.sh`, mirrored in `ashvm/tests/`.

## 2026-07-20 (Plan B, phase B5 completed — Windows DLL equivalent)
`--link=shared` now works for `--target=windows` too: compiled programs import from a real `libkilnrt.dll`, loaded and symbol-resolved by the actual Windows PE loader (Wine, in this environment — no Windows box available, same honest caveat as Plan A's PE work). - **New `pe_dll_writer.c`** — the PE twin of `elf_so_writer.c`: an `IMAGE_FILE_DLL`-flagged PE32+ file with a real Export Directory (function/name/ordinal arrays), exporting the same 5 runtime functions by name. One real correctness requirement ELF's hash-table lookup doesn't have: the Windows loader resolves imports-by-name via **binary search** over the Name Pointer Table, so that table has to be sorted lexicographically — got this right the first time by explicitly sorting rather than assuming enum-declaration order would happen to work.
- **Generalized `pe_writer.c`'s import table** (`pe_dynamic.c`, new) to support a SECOND imported DLL (`libkilnrt.dll` alongside `kernel32.dll` — previously hardcoded for exactly one) via a fully parallel `KILN_PE_SHARED_*` constant set, so `--link=static` output stays byte-for-byte unchanged (verified, not assumed). ## 2026-07-20 (Plan B, phases B2-B5 — real ELF dynamic linking for kiln)
kiln now supports `--link=shared`: compiled programs dynamically link against a real `libkilnrt.so` at runtime, loaded and symbol-resolved by the actual system dynamic linker (`/lib64/ld-linux-x86-64.so.2`) — not a kiln-invented format, a genuine SysV-ABI-compliant shared object inspectable with `nm -D`/`readelf`/`ldd` like any other `.so`. Chose the hard path deliberately after flagging the risk (hand-implementing dynamic-linking internals is real linker/loader engineering, not comparable in difficulty to anything else in this project, and a subtly-wrong implementation degrades to unpredictable segfaults rather than a clean error) — validated the entire binary format with a from-scratch Python prototype against the REAL linker before writing a line of kiln C code, catching two layout bugs (VA-vs-file-offset for `.dynamic`/`.rela` entries) at that stage instead of inside kiln's own codegen.
- **B2** position-independence: audited every runtime routine and found the ACTUAL scope was much smaller than expected — kiln's fixed, non-PIE executable load base means the globals region address is a genuine process-wide constant even for code that will live in an ASLR'd `.so` (the `.so` doesn't own the globals, whichever executable calls it does, and every kiln executable is fixed-base), so only `print_int.c`'s one embedded `"nil\n"` literal needed real RIP-relative addressing (new `emit_lea_rip_disp32`/`emit_lea_rip_back` primitives). Everything else either had no embedded data or already used relative jumps.
- **B3** `src/elf/elf_so_writer.c` — hand-written ET_DYN ELF64 shared object: SysV `.hash` (not GNU hash — simpler, still what real linkers accept), `.dynsym`/`.dynstr`, no section headers (matches this project's existing "tiny ELF" philosophy; `nm -D`/`readelf` don't need them, only `ld.so`'s own `PT_DYNAMIC`-driven parsing does, and that's section-header-free by design). Exports 5 functions via `codegen/runtime_exports.def` (X-macro, mirrors Plan A's `pe_imports.def` pattern): `kiln_heap_alloc`, `kiln_bytes_copy`, `kiln_string_alloc_prefixed`, `kiln_print_top`, `kiln_raise`.
- **B4** `src/elf/elf_dynamic.c` — the executable side: `PT_INTERP` (real system linker), `PT_DYNAMIC` with `DT_NEEDED=libkilnrt.so` + `DT_RPATH=/usr/local/lib/kiln`, a GOT with eager (non-lazy) `R_X86_64_GLOB_DAT` relocations — deliberately skipped lazy PLT-stub binding (real linkers' default) since it needs a resolver-callback dance with `ld.so` for zero behavioral benefit at kiln's scale. New `emit_call_abs32` primitive (`call [disp32]`, x86-64's absolute-displacement addressing mode) calls through a GOT slot touching **zero** general-purpose registers — necessary because kiln's 5 runtime routines each have their own fixed argument registers (`heap_alloc`: RDI/RAX, `print_top`: RAX/RBX, `bytes_copy`: RDI/RBX/RDX...), so no single register was safe to clobber loading the GOT address first without silently breaking one of them (`bytes_emit_copy` in particular documents RSI as preserved for callers — a register-based GOT-address scratch would have violated that contract).
- **B5** `make install-runtime` (root required, never run by `make all`) installs `libkilnrt.so` to the fixed RPATH.

One real, structural bug found via full-suite testing (not assumed away): the first working end-to-end version crashed on the very first heap allocation. Root cause was a conflated flag — `elf_so_writer.c` temporarily forced link mode to `static` while compiling the runtime, so that the runtime's own internal calls (e.g. `string_alloc_prefixed` calling `heap_alloc`) would resolve as local same-`.so` calls instead of GOT calls back into itself — but `codegen/layout.c`'s globals-address selection reads that SAME flag, and forcing it to `static` also silently made the runtime compute the WRONG globals address (the static-executable layout instead of the shared one) for its own heap pointer. Fixed by splitting into two independent flags (`KilnLinkMode` for "which layout owns the globals", `kiln_is_compiling_so()` for "should this routine's own calls be local or GOT-based") — the two questions looked identical but weren't.

Verified for real, not assumed: 29/30 `kiln/tests/*.ash` byte-identical between `--link=static` and `--link=shared` output (the 1 "difference," `argv.ash`, is `argv[0]` correctly reflecting each binary's own distinct filename — not a bug). `ldd` on a `--link=shared` binary shows the real `libkilnrt.so` dependency; `/lib64/ld-linux-x86-64.so.2` loads and resolves it with zero kiln-side involvement at runtime. Full 30/30 static-mode and Windows-target regression confirmed unaffected.

## 2026-07-18 (M8)
Kiln milestone 8: closures / first-class functions. Lambda literals (fn(params){body} as an expression), named functions used as bare values, and calls through a variable all flow through one uniform TAG_FUNCTION runtime shape -- a small, never-resized heap object: [0]=absolute code address, [8]=capture_count, then each capture's (tag,payload). Two real design problems solved before writing any code (see codegen/closures.c and lambda.c headers for the full reasoning): (1) a lambda's code address isn't known until after its body compiles, but the closure-creation code that embeds it runs first -- solved with a new "patchable imm64" primitive (emit_mov_reg_imm64_patchable / emit_patch_imm64), generalizing the project's existing emit-now-patch-later jump pattern to an absolute-address immediate. (2) capture_count is only known at runtime (read out of the closure object) and must survive the indirect `call` instruction, but every GP register is freely clobbered by the callee -- solved with a new fixed RBP-relative scratch slot (KILN_FRAME_RESERVE, one slot beyond the normal MAX_KILN_VARS table) rather than the CPU stack, since pushing extra data there would have shifted every existing parameter-offset formula the callee's prologue relies on.

Captures are snapshotted BY VALUE at closure-creation time (documented scope limit, same spirit as M7's linear-scan map note) -- every currently-visible outer variable is captured automatically, no free-variable analysis needed given the single-pass architecture. This supports partial application / currying and higher-order functions (a function returning a closure, a closure passed into another function) but not a closure that mutates a captured variable and expects that mutation visible on the next call (the classic "counter" idiom) -- that needs real upvalues (boxed variables), which conflicts with kiln's single-pass fixed-stack-slot variable model and is out of scope here.

New src/codegen/closures.c (object creation, named-function values, indirect calls) and lambda.c (lambda literal parsing/codegen), split to stay under the 200-line guideline. codegen_call in expr_call.c gained one new branch (variable resolves before function-name resolves) ahead of its existing direct-call path, which is otherwise untouched.

## 2026-07-18 (M9)
Kiln milestone 9: try/catch. A hand-rolled setjmp/longjmp equivalent, since this is a freestanding binary with no libc to call into -- a fixed-depth (MAX_KILN_TRY_DEPTH=16) handler stack living in the globals region (elf/elf_writer.h), each entry {saved_rsp, saved_rbp, catch target address, error-variable rbp-offset}. Every existing runtime error (array bounds, missing map key) now routes through one reusable "raise" routine (codegen/errors.c) instead of unconditionally dying: if a try is active it pops the innermost handler, restores RSP/RBP to their try-entry values (discarding however deep the call stack had gotten, including through function calls -- verified with an error raised inside a called function, unwinding cleanly back to the try), binds the message as a real TAG_STRING value at the handler's recorded slot, and jumps to the catch block; otherwise it falls through to the original write-to-stderr-and-exit(1) path, unchanged.

Two forward-reference problems, both reusing machinery already built for M8's closures rather than inventing new patterns: the catch block's absolute code address isn't known until after the try body compiles, so it's written via the same patchable-imm64 primitive lambdas use; and the catch variable's slot has to be reserved (for its rbp-relative offset, embedded into the handler struct at try-entry) before its real name is even parsed (`catch (e)` comes after the try body) -- solved with a new small vars.c primitive, rename_var, that reserves a placeholder slot up front and retroactively overwrites its name once `(e)` is seen.

Real bug caught during verification: a caught error's message was initially embedded as raw bytes for a direct syscall write, not as a proper length-prefixed string -- printing a caught error value directly (`catch (e) { print e; }`) read the 8 bytes before the message as its "length" and dumped raw code-segment bytes. Fixed by giving error messages the exact same length-prefixed layout codegen/strings.c's literals use, so a caught error is a fully legitimate string usable with print/concat/equality like any other.

New: a bounds check on the handler-stack push itself (exceeding MAX_KILN_TRY_DEPTH is treated as an unconditional fatal error, never catchable -- silently overflowing past the fixed table would corrupt the adjacent, writable code segment). Verified with a recursive function pushing a try 20 levels deep, dying cleanly instead of corrupting memory.

Scope trim: no explicit `throw` statement -- this milestone catches kiln's own existing runtime errors (array/map), not user-raised ones; deferred alongside the other scope trims already on record (M6's map/filter/reduce, M7's keys/values).

Verified: zero regression on the entire M1-M8 suite, plus catching an array-bounds error and a missing-map-key error (with normal execution continuing after each), a try whose body raises nothing (catch correctly skipped), nested try/catch (inner catches its own error, outer's handler correctly left untouched), an error raised deep inside a called function unwinding back to the try, and the uncaught (no try present) path still dying with the same message and exit status as before this milestone.

## 2026-07-18 (M10)
Kiln milestone 10: the remaining 23 ashvm builtins -- sqrt/abs/floor, str/num conversion, map/filter/reduce, keys/values, split/join/substring/indexOf/replace/upper/lower/trim, read_file/write_file/append_file/file_exists, input(). Every one hand-encoded, zero libc: math via new SQRTSD/ANDPD SSE primitives, file I/O via raw open/read/write/close/lseek syscalls, num()/str() via hand-written digit parsing and formatting (no strtod/snprintf).

Two real design points carried the rest: (1) map/filter/reduce needed to call an arbitrary closure value from INSIDE codegen, not from parsed `f(...)` syntax -- closures.c's codegen_indirect_call was split into a reusable tail, codegen_call_closure_value(argc), that assumes the closure and its arguments are already pushed. (2) most of these builtins need more live state across a loop (and across nested calls, which clobber every GP register) than the six general-purpose registers can hold at once -- extended the RBP-relative scratch-slot technique from M8/M9's call_scratch_offset into a full 128-byte higher_order_scratch_offset() region, reused with different field layouts by whichever builtin is currently running. Proven safe by the same reasoning as call_scratch_offset: source-level arguments evaluate left-to-right, so nested calls like map(map(a,f),g) never have two builtins "live" in the same scratch region at once, and a callback that itself calls another higher-order builtin runs in its OWN call frame (own rbp), landing at a completely different address.

Two real bugs caught during verification, both in newly-added machinery: editing vars.h to grow the frame-reserve constant didn't trigger a rebuild of files that only include it (not modify it) -- the Makefile had no header-dependency tracking, so a stale binary mixed old and new frame-size assumptions across functions and segfaulted. Fixed properly: -MMD -MP dependency generation, verified by touching a header and confirming the right files rebuild without a full clean. Second bug: input()'s byte-read loop used RSP directly as a byte-load base register, which this project's minimal instruction encoder explicitly doesn't support (needs a SIB byte it doesn't emit) -- same class of bug flagged in the existing emit.h comments for exactly this reason; fixed by copying RSP into RCX first, matching the pattern print_int.c already established.

Verified: zero regression on the entire M1-M9 suite, plus dedicated tests for every new builtin including edge cases (empty array/map/string inputs, out-of-range substring/indexOf, empty-delimiter split, empty-search replace, nested map(map(...)) calls, file round-trips through write/append/read, and piped stdin for input()).

## 2026-07-18 (M11)
Kiln milestone 11: `for (x in array) { block }` loops. The array expression evaluates once up front; the loop variable is bound to each element via the same var-slot mechanism `let` already uses (an ordinary, reassignable variable inside the body -- reassigning it doesn't affect iteration, matching a plain for-each's usual semantics).

Real design point: the loop's own state (data_ptr, count, running index) needs to survive whatever the body's own codegen does -- including calls, and including ANOTHER for loop nested inside it. Unlike M9's try/catch (genuinely runtime-recursive, needing a runtime-tracked handler stack) or M10's higher-order builtins (never concurrently active within one frame, since source arguments evaluate left-to-right), `for` loop NESTING is fully visible at COMPILE TIME -- nested `for` statements are literally nested calls in this single-pass compiler. So each nesting level just gets its own fixed RBP-relative offset (vars.h's for_level_offset(depth)) computed from a plain compile-time counter, bounded the same way every other table here is (MAX_KILN_FOR_DEPTH=8), rather than another runtime stack. The counter resets to 0 when entering a function or lambda body (mirroring vars_save/vars_clear/vars_restore) since that body gets its own RBP at runtime and can safely reuse the same offsets independently of the enclosing code's own nesting depth.

Verified: zero regression on the entire M1-M10 suite, plus a basic loop, nested for-in-for (i*j over two arrays), a loop body calling a higher-order builtin (map) without corrupting the outer loop's own iteration state, an empty array (body never runs), a for loop inside a recursive-capable function, and loop-variable reassignment inside the body not affecting which elements get visited.

This closes out the full M1-M11 roadmap from the original plan: Kiln now has variables, control flow, functions/recursion, real doubles, strings, arrays, maps, closures, try/catch, the complete ashvm builtin set, and for-in loops -- all hand-written x86-64 codegen and a hand-written ELF writer, zero external tools anywhere in the pipeline.

## 2026-07-19 (missing.md pass: correctness fix + language core + argv)
Addressed missing.md's #1 (correctness bugs), the tractable subset of #2 (language core), and #4's argv() -- deliberately deferring structs/classes, modules, multi-return/destructuring, spread/varargs, and nested-function scoping, each a standalone design effort rather than a bolt-on (see missing.md for the updated status).

**Correctness fix**: `arr[i]`'s read dispatch only branched on TAG_MAP vs "else assume array" -- `"hello"[0]` silently read a string's own content bytes as if they were an array-object struct instead of erroring. Added a real TAG_STRING branch (codegen/strings.c's codegen_string_index_read, bounds-checked, returns a 1-char string) and made index-assignment into a string a clean runtime error (strings are immutable). Found and fixed a second, unrelated pre-existing bug while testing this: two SEQUENTIAL (not nested) try/catch blocks reusing the same catch variable name created two table entries, and resolve_var's first-match-wins scan bound the second catch body to the first catch's stale slot -- fixed by scanning newest-first (standard shadowing semantics), parser/vars.c.

**Language core additions**: break/continue (a compile-time loop-context stack, parser/loop_stack.c, since continue's target -- the per-iteration advance step -- isn't emitted until after the loop body compiles, so it's forward-patched like break rather than backward-jumped); true/false/nil literals (true/false are sugar for NUMBER 1.0/0.0, not a new type; nil is a real new TAG_NIL whose payload is always exactly 0, which lets it ride the EXISTING truthy-test and numeric-comparison codegen for free); ternary a?b:c; bitwise operators (& | ^ << >> ~, one flat precedence level, new AND/OR/XOR/SHL/SAR/NOT emit primitives); compound assignment (+= -= *= /=, `+=` reusing the exact same tag-aware add codegen `+` uses, extracted into codegen_apply_plus) and ++/--; exponent `**` (integer exponents only, via exponentiation-by-squaring -- a genuine runtime loop since the exponent is only known at runtime, unlike every other operator here; no x87 FYL2X/F2XM1 in this SSE2-only project, so fractional exponents are out of scope); hex/scientific-notation/underscore numeric literals (the lexer only had to stop truncating the token early -- strtod(), real libc, already runs at COMPILE TIME on the host in expr.c's primary() and natively parses "0x1A"/"1e10"; underscores are the one thing it doesn't understand, stripped into a clean buffer first); block comments; throw (reuses codegen/errors.c's raise routine with a new dynamic-message variant, errors_emit_die_dynamic, for a runtime string instead of a compile-time-constant one); and kiln's missing unary `!` (ashvm had TOKEN_BANG -> OP_NOT all along, kiln never wired it up).

Saved to a new fixed globals address (KILN_ARGV_ADDR) as compile_program's literal first instruction, reachable from any frame later (a called function's own RBP is no longer the original one). codegen/argv_builtin.c walks the raw C-string argv array (kernel-provided, NOT length-prefixed -- needs its own strlen scan) building a real kiln array of length-prefixed strings.

Verified: zero regression on the entire M1-M11 suite at every step (18 test files), plus dedicated new tests for every item above, including edge cases (nil vs 0 vs false tag-distinctness, chained/nested ternary, negative and chained exponents, sequential non-nested try/catch with the same variable name, throw unwinding out of a function call, argv() with and without extra arguments).

## 2026-07-20 (block scoping)
Closed missing.md's block-scoping gap: kiln's variable table was one flat, append-only, per-*function* name->slot array -- `if`/`while`/`for`/`try`/`catch` bodies called the shared `block()` helper with no scope bracketing of their own, so a `let` declared inside stayed resolvable for the rest of the enclosing function forever, and re-`let`-ing a name that already existed anywhere in the function REUSED that slot (mutating it) rather than creating an independent inner binding. `for_loop.c`'s loop variable and `try_catch.c`'s catch variable had the identical pattern, declared outside their own `block()` call.

Fix reuses a pattern already in the codebase for exactly this shape of problem (compile-time nesting state, saved/restored across recursive descent -- the same technique as `for_depth_save/restore` and `loop_depth_save/restore`): a new `scope_start` mark in `parser/vars.c`, paired `vars_scope_begin()`/`vars_scope_end()` bracketing `block()` itself (covers if/while/try-body/catch-body/fn-body/lambda-body in one choke point) plus `for_statement()`/`try_statement()` themselves (their loop/catch variable lives outside their nested `block()` call). A new `resolve_var_in_current_scope()` (scans only slots >= `scope_start`) replaces the full-scan `resolve_var()` in `let_statement`'s and `for_statement`'s reuse-or-declare check specifically, so a name only visible from an enclosing scope shadows instead of mutating; every plain read/`=`/compound-assignment/index-assignment site keeps using the unchanged full-scan `resolve_var()`, since those must still reach into enclosing scopes.

Checked against `closures.c`/`lambda.c` before writing any code: scope enter/exit is compile-time-only (zero runtime instructions, just static slot-index bookkeeping), and lambda capture copies each captured variable's value into the heap closure object at the moment the lambda literal is evaluated -- always before the enclosing block's `}` is reached, so slot reuse afterward can't corrupt an already-captured closure. Confirmed with three dedicated tests rather than just assuming it: a closure created and returned from inside an `if` block whose capture slot is later reused, a closure capturing a variable that shadows an outer same-named one (closure sees the inner value, outer stays untouched), and closures created per-iteration inside a `while` body each keeping their own snapshot.

One existing test depended on the very leak being fixed: `for_loops.ash`'s trailing `print x;` after a `for (x in nums) {...}` loop relied on the loop variable leaking (previously printed `1030`, the last iteration's mutated value); removed, since the reassignment-doesn't-affect-iteration behavior it was piggybacking on is already covered by the three prints inside that same loop body.

New tests: `block_scoping.ash` (shadow-vs-mutate, plus 20 sibling if-blocks x 4 unique variables each to prove slot reuse rather than leaking into `MAX_KILN_VARS`'s 64-slot ceiling), `block_scoping_closures.ash` (the three closure-interaction cases above), `for_loop_scoping.ash` (loop variable no longer leaks or mutates an outer same-named variable; nested loops with the same variable name at each level stay independent), `try_catch_scoping.ash` (catch variable scoped to its own statement; a second, previously-unentered `catch (e)` no longer shadows the first via a garbage, never-written slot).

Verified: zero regression on the entire M1-M11 + missing.md-pass suite (every file's output byte-identical before/after, via a new `kiln/tests/run_regression.sh` baseline/diff harness) except `for_loops.ash`'s intentional, documented change above, plus the four new test files and negative compile-error checks (referencing a block/loop/catch-scoped variable after its block now fails cleanly with `undefined variable: <name>` instead of silently resolving to a leaked or mutated value).

Still open per missing.md: modules/imports, structs/classes, switch/match, multi-return/destructuring, spread/varargs/default params, nested/private functions.
