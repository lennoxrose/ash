## 2026-10-08 (the rest of the language gaps ash-json found)
Second batch; the numbers in parentheses are the entries of ash-json's list of language gaps. Every change is on both `ashvm` and `kiln` with a test in each `tests/cases/` tree, and the regression diffs below were checked against a baseline built from the previous commit (the intended ones: booleans printing as `yes`/`no`, insertion-ordered maps, the new number format, unified error wording). As before, there is deliberately no `remove` builtin (ash-json defines its own `remove` functions, and a builtin name would shadow them); `delete(array, i)` covers it.

**Booleans (4):** new value type. `yes`/`no`, comparisons, `not`, `and`/`or`, `has`, `file_exists`, `contains`/`starts_with`/`ends_with`, `rename_file`/`delete_file`/`make_dir` and `write_file`/`append_file` produce it. Prints `yes`/`no`, `type()` is `"boolean"`, `str(yes)` is `"yes"`, `yes == 1` is false (arithmetic and truthiness still treat it as 1/0). `ashvm`: `VM_BOOL`, `vm_values_equal()` (also gives arrays/maps/functions identity equality, as kiln already did). `kiln`: `TAG_BOOL`. Conditions on both engines now accept booleans, numbers and `none` and raise `invalid operand type in condition` for a string/array/map/function (kiln used to treat a map as truthy; `kiln` has one `codegen_pop_and_test_truthy` instead of three copies). `filter` accepts a boolean-returning predicate.

**Insertion-ordered maps (3):** `ashvm`'s open-addressing table became a dense entry list plus an index (deleting no longer leaves probe-chain holes, which also fixed lookups after a delete); `kiln`'s `delete` shifts later entries down instead of swapping in the last one. `keys`/`values`/printing agree on both.

**Number format (8):** one format for both engines. `ashvm` used `%lld`/`%g` (6 significant digits), `kiln` printed 6 fraction digits and produced garbage past int64. Now: integers plainly below 1e15, otherwise up to 6 fraction digits with trailing zeros dropped, and scientific (`1e+21`, `1.5e-07`) at or above 1e15 / below 1e-6; `nan`/`inf`/`-inf`. `kiln`: `codegen/C/runtime/number_format.c`, shared by `say` and `str` (it replaces two copies and also fixes a carry bug at `x.9999999`); `ashvm`: `vm_format_number`. 6 fraction digits is not shortest-round-trip; that stays a documented limit.

**`var.field` and `e.message` (9):** `x.name` on a local variable is `x["name"]`; indexing a string with a string yields the string itself, so `handle (e) { say e.message; }` works for built-in errors (strings) and raised maps alike on both engines.

**Error wording and structured errors (9):** caught messages are identical on both engines and carry no prefix or detail (`index out of bounds`, `key not found`, `invalid operand type in '+'`, `could not open file`, ...); `kiln` adds `error: ` itself when an error is uncaught. `raise` takes any value (`kiln`'s raise routine now carries the value's tag), so `raise {"kind": "parse", "line": 3}` is caught as a map. Built-in errors remain strings (making every caught error a map would break `"x: " + e`); `ashvm` also gained string indexing `s[i]` to match `kiln`.

**Sort (6):** `sort(array)` / `sort(array, cmp)`, in place, stable, returns the array; `cmp(a, b) > 0` means `a` goes after `b`. `ashvm`: merge sort; `kiln`: insertion sort (O(n^2)).

**Files (17):** `rename_file`, `delete_file`, `make_dir`, `list_dir` (names without `.`/`..`, directory order). Windows `kiln` targets get real `MoveFileA`/`DeleteFileA`/`CreateDirectoryA` imports, and `list_dir` walks `FindFirstFileA`/`FindNextFileA`/`FindClose` (shared with the Linux path through `emit_add_entry`). The Windows code is verified by running it: `kiln/tests/scripts/windows_emulated_check.sh` executes each test case's PE under the Unicorn emulator with a Python stand-in for kernel32 (real files underneath), and all 63 runnable cases match their Linux builds, `fs_ops` included. The same cases also match under Wine 11.19 (`windows_wine_check.sh`), including `C:\\` paths for the file operations, which removes the dependence on my own kernel32 stand-in. Neither is real Windows.

**Strings (18, 19):** `contains`, `starts_with`, `ends_with`, `repeat`. Complexity, as requested: strings carry their length now on `ashvm` (`len`, `substring`, `s[i]` no longer `strlen`), and are length-prefixed on `kiln`, so `len`/`s[i]` are O(1) and `substring` O(piece). `s += x` copies the whole string (quadratic over a loop, and nothing is freed); `join(parts, "")` is the linear builder. `kiln`'s `push` grew arrays by 4 slots per reallocation (quadratic memory against its 16 MB bump heap, so a 200k-element array crashed); it doubles now.

**Builtins as values (11):** `type(len)`, `map(xs, str)`, `local f = len;` compile a one-line wrapper lambda by re-lexing a synthesized `forge (a0, ...) { yield name(a0, ...); }`. Variadic builtins (`sort`) wrap with their minimum arity.

**Forward declarations (13):** a pre-pass over each file reserves every named `forge name(params)` (with its arity), so calls can precede the definition and functions can call each other. `ashvm`: `compiler/C/prescan.c`; `kiln`: calls to a not-yet-defined function emit a placeholder that is patched when the body is compiled (`function_add_call_fixup`/`function_resolve_fixups`). A reserved name that is never defined is `undefined function`. A local variable now shadows a function of the same name on `ashvm` too (kiln already did).

**Imports (14, 15, 16):** `@import <file.ash> as name;` chooses the namespace. Transitive imports are now documented (README) and covered by `imports_transitive_test`. Every top-level `local` of an imported file is a module-level variable: its expression runs once where the `@import` is, the file's functions read it and update it (`NAME = ...;`, `NAME += ...;`, `NAME++;`, `NAME[i] = ...;`), and `file.NAME` reads it from outside. `ashvm`: `OP_GET_GLOBAL`/`OP_SET_GLOBAL` (256 slots); `kiln`: a 128-slot table in the globals region of every binary (+2 KB). It replaces the old "literal number/string constant only" rule (such constants were read-only).

**Smaller (7, 10, 12, 20, 21):** exponent literals and `num("1.5e2")` already landed in the first batch; `exit(code)` ends the program with a status (an uncaught error exits 1), which is what a test runner needs; the `kiln` output that "silently stopped" after `attempt { delete(array, 0); ... }` came from `delete` treating an array as a map and is gone now that `delete(array, i)` exists (`attempt_array_delete` covers it).

**Not done:** nothing left from that list.

## 2026-10-08 (language gaps found by ash-json: function limit, `attempt` unwinding, short-circuit, string order, `chr`/`ord`, array mutation, more)
First batch from the ash-json 0.2.0 needs list (numbers are the entries of ash-json's list of language gaps). Everything below behaves the same on `ashvm` and `kiln` and has a test in both `tests/cases/` trees.

**Function limit (0):** `MAX_VM_FUNCS` / `MAX_KILN_FUNCS` 64 -> 1024, so `@import <ash-json>;` (87 functions) loads.

**Stale `attempt` handlers (9b):** two separate causes. `ashvm`: after a `longjmp`, `do_TRY_PUSH`'s recovery branch read its plain local `h`, which still pointed at a later, already-popped nested handler, so a caught error restored the wrong frame/stack. It now re-derives the handler from `try_depth`. Both engines: leaving an `attempt` block early with `yield`, `stop` or `next` skipped the handler pop, so the handler stayed active for the rest of the program. The compilers now count open `attempt` blocks per function (`attempt_enter`/`attempt_leave` in each `loop_stack.c`, which also remembers the count at loop entry) and emit the handler pops before those jumps/returns. No VM cost; kiln had this bug too (found by the new test).

**`and` / `or` short-circuit on `ashvm` (10a):** compiled to `OP_JUMP_IF_FALSE` plus the old `OP_AND`/`OP_OR` against a constant (to keep the result 0/1); no new opcode.

**String `<` `>` `<=` `>=` (1):** bytewise on both engines. `ashvm`: one `ORDER` macro used by the four ops and the fused `OP_CMP_JUMP`. `kiln`: `codegen_string_order()` leaves cmp-style flags that `push_bool` consumes like `ucomisd`'s. Mixed string/number is still a type error on `ashvm`; kiln keeps its "assume number" limit there.

**`chr(n)` / `ord(s)` (2):** byte <-> one-byte string. `chr` takes 1..255 (`ashvm` strings are C strings, so no 0), `ord` of `""` is an error.

**Arrays (5):** `delete(array, i)` removes at an index (returns the array, like `delete(map, k)`), plus new `pop(array)`, `insert(array, i, v)` (`i` may equal `len`) and `slice(array, from, to)` (`[from, to)`, strict bounds). kiln: `codegen/C/collections/array_mutate.c`; `insert` validates first, then reuses `push()` for growth. Not added as `remove`: ash-json defines functions called `remove`, and a builtin name shadows user functions.

**Numbers (7, 12):** `ashvm` lexes exponent literals (`1e3`, `1.5e-3`) like kiln already did; kiln's `num()` now parses `e`/`E` exponents (`num("-1.5e2")` was `-1.5`).

**Type errors (10, 10b):** kiln `"x" + 1` / `1 + "x"` and `str("text")` now raise (`invalid operand type in '+'`, `str() expects a number`) instead of returning garbage.

**Still open at this point:** everything not listed above; the rest of the list is in the next entry up.

## 2026-10-07 (three more parity bugs, found verifying the JSON module before handing it off)
Before writing `mission.md` (a hand-off doc for shipping the first real `forgepack` module — a JSON codec in pure Ash), actually ran the module's code through both engines rather than just writing it and hoping. Found three more real bugs this way, on top of `type()` above — the module itself was the test case the existing regression suites never exercised (real, non-trivial, deeply-nested-and-recursive user code, not hand-picked feature probes).

**Bare reassignment (`x = expr;`, no `local`) didn't exist on `ashvm` at all.** A known, previously-*documented*-but-never-fixed gap from an earlier session (flagged when asked "are both engines exactly the same" — the honest answer was no, citing this exact example) — writing a parser that reassigns a position variable throughout (`i = json_skip_ws(s, i);`) finally made it a hard blocker instead of a noted gap. `identifier_statement()` (`compiler/C/stmt.c`) handled a call, an index-assign, compound-assignment, and `++`/`--` on an already-declared variable, but fell through to "unexpected identifier statement" for a plain `=`. `kiln` already supported this (`assignment_statement()` always reassigns an existing slot). Fixed by adding the missing case: `OP_SET_LOCAL` after a full `expression()`, same as `local_statement()`'s own "already declared" path.

**A namespaced call used as its own statement didn't parse on either engine.** `json.save(path, value);` (the entire point of a `save()` function — call it for the side effect, don't use its result) failed on both: `ashvm` with "unexpected identifier statement", `kiln` with "expected '=' after variable name". `module.func(...)` as part of an *expression* (`local x = json.load(...);`) already worked (`expr.c`'s `primary()` has a `TOKEN_DOT` case) — the gap was specifically the bare-statement entry points (`identifier_statement()` on `ashvm`, `assignment_statement()` on `kiln`), which checked for a plain call, an index-assign, etc., but never checked for `TOKEN_DOT` before falling through. Fixed by mirroring the exact dotted-call logic from each engine's own expression parser, with a trailing `OP_POP`/pop-pop to discard the unused return value, matching how a bare non-namespaced call statement already does.

**Import compiler rejected any `local` inside an imported function's own loop.** `try_declare_import_constant()` (the mechanism that lets a top-level `local NAME = <literal>;` in an imported file become a namespaced compile-time constant, e.g. `mathlib.PI`) was called unconditionally for *every* `local` statement anywhere in an imported file's compiled body — including deep inside one of that file's own functions, since the "currently compiling an imported file" flag is set once for the whole file, not scoped by block depth. Every `local` inside `json_skip_ws`'s loop (`local c = substring(s, i, i + 1);`) got misdiagnosed as a failed attempt at a top-level namespaced constant ("imported top-level 'local' must be a literal number or string constant") even though it's three blocks deep, nowhere near the file's top level. The sibling guard in `statement()` already correctly checks `block_depth == 0` for the analogous "only forge/local allowed at top level" restriction — this specific call site just never got the same check. One-line fix, mirrored on both engines.

All three fixes verified together: the full JSON module (parse/stringify/load/save, nested arrays-of-objects-of-arrays, malformed-input error handling via `attempt`/`handle`) now runs byte-for-byte identical on both engines, including a fourth bug that was in the *module's own code*, not the engines — `json_parse_string`'s loop had no end-of-input check (`during yes` with only "found a closing quote" as the exit condition), so an unterminated string in malformed input scanned forever: OOM-killed on `ashvm`, segfaulted on `kiln` (its bump allocator has no bounds check once the arena's exhausted). Fixed in the module, not the engines — bounded the loop on `i < len(s)` and `raise` on falling through.

## 2026-10-07 (`type()` builtin, both engines)
A genuine gap found while designing the first real `forgepack` module (a JSON library): there was no way for pure Ash code to ask a value what it *is*. Every existing builtin either requires a specific type already (`keys()`/`has()` error on a non-map, `upper()` on a non-string, ...) or works the same way regardless of type (`len()`). A general `json.stringify(value)` has to decide "format this as an array vs. a map vs. a string vs. a number" from an arbitrary value with no static type — there's no way to do that without some form of runtime introspection.

Added `type(value)` → `"number"/"string"/"array"/"map"/"function"/"none"` to both engines. `ashvm`: builtin id 27 (`builtins/C/core.c`, `builtins/C/builtins.c`), a straight switch on `VMValue.type`. `kiln`: a new module (`codegen/C/builtins/type_builtin.c`) — pop the value's tag, branch, and push one of six pre-embedded string literals via the already-existing `codegen_string_literal_bytes()` (the exact same length-prefix-embedding helper regular string literals use, so the result is a completely ordinary string value, not a special case). `ashvm`'s own print path distinguishes `"<function>"` vs. `"<closure>"` (see the array/map-printing fix further down this file), but `kiln` has no separate closure tag at all to match that with — `type()` collapses both to `"function"` on `ashvm` too, so the two engines agree on every possible result, rather than exposing a distinction only one side can make.

## 2026-10-07 (four cross-engine parity bugs, found by a side-by-side audit)
Ran the same `.ash` source files through both engines and diffed stdout byte-for-byte, which the previous entry's feature-parity work made possible for the first time (no point diffing output that couldn't even be compared before). Found four real bugs — three in `kiln`, one `ashvm`-only — fixed all four, then re-ran the audit to confirm convergence. The only remaining difference across every test file is map iteration order (`keys(m)`/`values(m)`), which is a documented, pre-existing architectural difference (`ashvm`'s real hash table vs. kiln's dense insertion-ordered array, see `codegen/H/emit/value.h`) and not a bug — neither engine's map iteration order was ever a language guarantee.

**`kiln`: missing `%` operator.** `TOKEN_PERCENT` was lexed but `term()` in `codegen/C/expressions/expr.c` only handled `*`/`/` — every `kiln` test needing modulo worked around it with `x - floor(x / n) * n`, which is a *different* operation for negative operands (floor-based mod vs. truncate-based `fmod`). Implemented as `a - trunc(a / b) * b` using the SSE2 primitives `floor()`'s codegen already established the pattern for (`emit_cvttsd2si` truncates toward zero directly, no separate correction step needed the way `floor()`'s overshoot-fix does) — matches `ashvm`'s C `fmod()` exactly, including sign: `-7 % 3 == -1`, not `2`. Verified identical output on both engines across positive, negative, and fractional operands.

**`kiln`: `say`-ing an array or map directly crashed or printed garbage.** `codegen/C/runtime/print_int.c`'s single print routine only ever had cases for `TAG_STRING` and `TAG_NIL`; anything else (including `TAG_ARRAY`/`TAG_MAP`, and, it turns out, `TAG_FUNCTION`) silently fell into the number-formatting path and tried to print a heap pointer as a double. This is why `kiln`'s own test suite never caught it: every test that uses `map()`/`filter()`/`keys()`/etc. immediately indexes into the result rather than printing it directly. Fixed with a new recursive printer (`emit_print_recursive_routine`, self-`call`s for nested arrays/maps, quotes string elements the way `ashvm`'s `vm_print_value()` does, falls back to `<function>` for anything else) plus a `number_routine` extracted out of the old inline digit-building code so both the recursive printer and the top-level routine can share it without duplicating ~90 lines of SSE2 asm. Wrote and threw away three register-clobbering bugs getting this right — hand-rolled x86-64 means `write_one_char()` (every bracket, comma, quote) clobbers RAX/RCX/RDX/RSI as a side effect of its own `write(2)`/`WriteFile` call, so anything that needs to survive across one has to live in memory (this routine's own `push rbp`-anchored frame, `[RBP-8/-16/-24/-32]`, *not* `[RSP+disp]`, which this codegen layer can't even encode — `RSP` as a base needs a SIB byte `modrm_mem_disp32()` doesn't emit), never in a register held "across" the call. Found via `gdb` on the raw statically-linked ELF (no section headers, no symbols — breakpoints by address, registers read at the exact instruction before/after a suspect load) after the first version printed `[1, ]` for `[1, 2]` instead of `[1, 2]`: traced to the loop's "index + 1, maybe print a comma, then store the new index" sequence holding the incremented index in `RCX` across the two `write_one_char(',')`/`write_one_char(' ')` calls that immediately clobber it.

**`kiln`: `len()` on a string read garbage.** `codegen_builtin_len()` in `codegen/C/collections/arrays.c` unconditionally read offset `+8` as "the count" — correct for `TAG_ARRAY`/`TAG_MAP` (they share the same `[capacity][count][data/entries_ptr]` object shape), but a string's length lives at offset `-8` from its payload (the length prefix that precedes the raw bytes), not `+8`. `len("hello")` was reading whatever garbage byte happened to sit 8 bytes into the string's own content. Fixed by branching on `TAG_STRING` first.

**`ashvm`: a fresh `local` declared inside a re-executed block (a `during`/`each` body, or a `given`/`otherwise` branch nested inside one) leaked a stack slot every pass instead of being replaced.** `ashvm` has no explicit "store a local" instruction — declaring one just means "whatever's on top of the stack now has this name," at a compile-time-fixed slot index (`frame->slots[n]`). `each`'s own three setup slots (array/index/var) already got cleaned up once, after the whole loop exits — but nothing cleaned up locals the *body* itself declared, every single iteration, and `given`/`during` didn't clean up after themselves at all. First iteration of `local x = i * 10; say x;` inside a `during` loop pushes `x` correctly; every iteration after that pushes *another* copy on top without popping the old one, while the compiled `OP_GET_LOCAL` for `x` keeps reading the same fixed slot index — the first iteration's value, frozen forever. `kiln` doesn't have this bug (confirmed directly, contradicting an assumption in the previous entry that this was some shared/inherited limitation): its locals are fixed `rbp`-relative memory addresses, not stack positions, so re-declaring one just overwrites the same address.

Fixed with a new VM instruction, `OP_TRUNC_LOCALS n` (`stack_top = frame->slots + n`) — an *absolute* reset, not a fixed number of `OP_POP`s, because a block can exit early (`next`, or one branch of a nested `given`) having declared fewer locals than its "normal" path does, so only the known target depth is ever safe to assume. `compile_given_stmt`/`compile_during_stmt`/`compile_each_stmt` each save `local_count` before their re-executed block, then call a shared `truncate_block_locals()` right where `next` already lands (before the per-iteration advance, so both the normal fallthrough and an early `next` converge on the same cleanup) — compiled to nothing extra when a block doesn't declare any locals of its own, so the common case (most loop bodies) costs zero bytes and zero instructions beyond what was already there. Verified against `fib.ash`/`loop.ash` (unaffected — this machine's own baseline for both, checked against the pre-session commit with a throwaway `git worktree`, already sits well above `AGENTS.md`'s reference numbers, which are from different hardware) and against deliberately adversarial cases (nested `given`/`next` inside `during`, nested `each` inside `each`) diffed byte-for-byte against `kiln`.

## 2026-10-07 (bring `ashvm` to the same feature level as `kiln`)
The reverse direction of the earlier kiln-parity work: `kiln` had six capabilities `ashvm` didn't (`stop`/`next` loop control, `raise` with a runtime string message, compound assignment, `++`/`--`, a ternary, and bitwise operators), plus `yes`/`no`/`none` literals from the same-day rename work. All ported, staying entirely within `ashvm`'s own execution model (interpreted bytecode VM, not compiled to native code like kiln) — this is language-feature parity, not architecture parity.

**`none` (nil) — the one real new concept, not just a port.** `ashvm`'s value representation had no null type at all (`VMType` was `{VM_NUM, VM_STR, VM_ARRAY, VM_MAP, VM_FUNCTION, VM_CLOSURE}`). Added `VM_NIL` and `vm_nil()` to `value/H/value.h`+`value/C/value.c`, then threaded it through every place a value's type is inspected: `truthy()` in `vm/C/errors.c` now treats `none` as always-falsy without erroring (matching kiln's "nil's payload is always exactly 0" rule) instead of the default "non-number errors" path every other truthiness check still takes; `do_EQ`/`do_NEQ`/`do_CMP_JUMP`'s equality branch in `vm/C/dispatch.c` gained a `VM_NIL == VM_NIL` case (including the fused-comparison path, which can reach it since `x == y` where both are locals holding `none` at runtime is a fusable `identifier CMP identifier` shape even though `x == none` itself never fuses — `none` is a keyword, not a number or identifier); `vm_print_value()` prints `none`. No existing builtin needed a change — `len()`, `str()`, etc. already reject unexpected types generically, so `none` just became one more value their existing type checks correctly refuse.

**`stop`/`next`** — a new `compiler/C/loop_stack.c`+`H/loop_stack.h` module (mirrors kiln's `parser/C/statements/loop_stack.c`), forward-jump bookkeeping per nesting level, no new VM instructions (reuses the existing `OP_JUMP`). Wired into `compile_during_stmt`/`compile_each_stmt` (`loop_push()` before the body, `loop_patch_nexts()` right before the per-iteration advance step, `loop_pop_and_patch_stops()` after) and `compile_forge_decl`/`lambda_literal` (save/reset/restore the loop-nesting depth around a function/lambda body, so `stop`/`next` inside one can't reach an enclosing loop it's textually written inside — ashvm's functions get their own `Chunk`, so a cross-chunk jump offset would be nonsense bytecode anyway; this turns that into a clean compile error instead). One genuine ordering subtlety for `each`: `stop` jumps and the loop's own condition-false exit both have to land at the *exact* same bytecode position (right before the each-loop's three cleanup `OP_POP`s, not after) so both paths fall through into the same cleanup — tested explicitly with nested `each` loops to confirm `stop` only breaks the innermost one and the stack stays balanced either way.

**`raise`** — needed a new opcode (`OP_RAISE`) and a new VM entry point (`vm_raise_value()` in `vm/C/errors.c`), since every existing runtime error goes through a fixed-size `char error_message[512]` buffer (fine for compile-time format strings, not for an arbitrary-length runtime string value). Added `raised_value`/`has_raised_value` globals (`vm/H/state.h`) that `vm_raise_value()` sets right before unwinding and `do_TRY_PUSH`'s recovery branch checks first, falling back to the `error_message` copy path for every other kind of error — so a caught `raise` hands back the exact raised string, not a truncated-at-512-bytes copy.

**Compound assignment / `++`/`--`** — deliberately *not* using the existing `OP_ACC_LOCAL` fused op (that only accepts a number-or-local operand, not a general expression — `x += f() + 1;` needs the full `GET_LOCAL, expression(), <op>, SET_LOCAL` path). `+=` reuses `OP_ADD` directly (same tag-aware string-concat-or-numeric-add logic `+` itself has); `-= *= /=` are number-only, same as `- * /` themselves. It's about cleanliness first: you can see where something lives from the path alone, no directory goes past ~14 files, and generated output never sits in the middle of hand-written code. It should also be far better to maintain: adding a module means one obvious place per file type, and the Lua-style high-level rework planned in `plans.md` will touch the lexer and compiler without having to dig through hundreds of files.

- **kiln:** `codegen/` split into `emit`, `expressions`, `functions`, `runtime`, `collections`, `strings`, `builtins`, `io` and `platform`; `parser/` split into `core`, `statements`, `declarations` and `imports`. `lexer`, `elf`, `pe`, `diagnostics` and `app` (`main.c`, `target.c`) got the four trees without extra feature folders, since they are small.
- **ashvm:** same four-tree layout for every subsystem (no `D/` tree, because its Makefile never produced dependency files); `common.h` moved to `app/H/`.
- **Makefiles:** both build objects into the `O/` trees (and kiln dependency files into `D/`) through one generated compile rule instead of in-place `.o` files. `.DEFAULT_GOAL` is pinned to `all`. `make clean` now deletes only `*.o`/`*.d` files so the folders survive, and every `O/` directory has a `.gitkeep` so the empty trees stay in git.

## 2026-07-21 (modules/imports + library storage, both engines)
kiln and ashvm both now support `@import <./relative/path.ash>;` and `@import <libname>;` (the latter resolving to `ash.libs/<libname>/<libname>.ash`), with imported functions and constants accessed via namespaced `ns.func(...)`/`ns.CONST` syntax. Implementation is source-level recursive merge, matching the design spec's Approach A: no linker, no new object format — the parser recursively parses an imported file's `fn` declarations and literal top-level `let` constants inline and registers them under a namespaced name (e.g. `"math.add"`) in the same flat function/constant tables everything else already uses. Constants are compile-time-folded to their literal value at each `ns.CONST` use site, not stored as real runtime state. Diamond dependencies (the same file reached via more than one import path) dedup by canonical filesystem path; circular imports and namespace collisions (two different files/libraries deriving the same auto-namespace) are both compile errors, with the collision message naming both colliding resolved paths. Verified by a real regression suite on both engines: `kiln/tests/imports_basic.ash`, `imports_lib.ash`, `imports_const.ash`, `imports_diamond.ash`, `imports_circular_check.sh`, `imports_collision_check.sh`, mirrored in `ashvm/tests/`.

**Explicitly not done here, by design (see `docs/superpowers/specs/2026-07-21-kiln-modules-imports-design.md`'s accepted tradeoffs), not oversight:** no library installer tool (no npm-equivalent fetch/publish mechanism — this only builds where libraries live and how they resolve/compile in); no real global mutable variable storage (constant folding solves the importable-constant case only, not shared mutable state across functions); no caching/incremental compilation (every imported file is recompiled from source on every build).

## 2026-07-20 (Plan B, phase B5 completed — Windows DLL equivalent)
`--link=shared` now works for `--target=windows` too: compiled programs import from a real `libkilnrt.dll`, loaded and symbol-resolved by the actual Windows PE loader (Wine, in this environment — no Windows box available, same honest caveat as Plan A's PE work). Plan B is now fully complete on both platforms.
- **New `pe_dll_writer.c`** — the PE twin of `elf_so_writer.c`: an `IMAGE_FILE_DLL`-flagged PE32+ file with a real Export Directory (function/name/ordinal arrays), exporting the same 5 runtime functions by name. One real correctness requirement ELF's hash-table lookup doesn't have: the Windows loader resolves imports-by-name via **binary search** over the Name Pointer Table, so that table has to be sorted lexicographically — got this right the first time by explicitly sorting rather than assuming enum-declaration order would happen to work.
- **Generalized `pe_writer.c`'s import table** (`pe_dynamic.c`, new) to support a SECOND imported DLL (`libkilnrt.dll` alongside `kernel32.dll` — previously hardcoded for exactly one) via a fully parallel `KILN_PE_SHARED_*` constant set, so `--link=static` output stays byte-for-byte unchanged (verified, not assumed). One real layout bug caught here: the two DLLs' IAT regions were interleaved (ILT_k32, IAT_k32, ILT_rt, IAT_rt), which broke the optional header's IAT data directory (a single `{RVA,Size}` pair can only describe one *contiguous* range) — fixed by grouping both ILTs before both IATs.
- **New `win_call_runtime_import`** for calling into `libkilnrt.dll`: needed a genuinely different mechanism than `win_call_import`'s kernel32 calls, and not just cosmetically. kiln's runtime routines use kiln's own bare per-routine register conventions (not the Windows ABI), so — same reasoning as the Linux GOT call — no register was safe to clobber loading the IAT address first. Linux's fix (`call [disp32]`, absolute-displacement addressing) doesn't carry over: kiln's PE image base (`0x140000000`) is already past the 32-bit absolute-displacement range. `call [rip+disp32]` does work, since everything in a PE image is close together, and still touches zero registers.
- One real, structural bug found by testing the Windows shared build under Wine (not assumed correct from the Linux case): `pe_import_addr()` — used by every EXISTING kernel32 call site (`VirtualAlloc`, `WriteFile`, ...) — unconditionally returned the static-mode IAT address, even in shared mode, where kernel32's IAT sits at a different offset (a second DLL's import machinery is now ahead of it). Every kernel32 call in a shared-mode Windows binary was jumping through the wrong slot — manifested as a jump to a garbage address on the very first `VirtualAlloc` call, caught immediately by running under Wine rather than trusting the structural PE checks alone.

Verified for real: 29/30 tests byte-identical between `--link=static` and `--link=shared` output for `--target=windows` too (same `argv[0]`-filename non-bug as Linux), all executed under Wine, not just structurally validated. Both static-mode paths (Linux and Windows) confirmed fully unaffected — 0 regressions across the whole matrix (static/shared × Linux/Windows). `make runtime-dll` builds `libkilnrt.dll`; no install step needed on Windows (standard DLL search order checks the launching `.exe`'s own directory first).

## 2026-07-20 (Plan B, phases B2-B5 — real ELF dynamic linking for kiln)
kiln now supports `--link=shared`: compiled programs dynamically link against a real `libkilnrt.so` at runtime, loaded and symbol-resolved by the actual system dynamic linker (`/lib64/ld-linux-x86-64.so.2`) — not a kiln-invented format, a genuine SysV-ABI-compliant shared object inspectable with `nm -D`/`readelf`/`ldd` like any other `.so`. Chose the hard path deliberately after flagging the risk (hand-implementing dynamic-linking internals is real linker/loader engineering, not comparable in difficulty to anything else in this project, and a subtly-wrong implementation degrades to unpredictable segfaults rather than a clean error) — validated the entire binary format with a from-scratch Python prototype against the REAL linker before writing a line of kiln C code, catching two layout bugs (VA-vs-file-offset for `.dynamic`/`.rela` entries) at that stage instead of inside kiln's own codegen.
- **B2** position-independence: audited every runtime routine and found the ACTUAL scope was much smaller than expected — kiln's fixed, non-PIE executable load base means the globals region address is a genuine process-wide constant even for code that will live in an ASLR'd `.so` (the `.so` doesn't own the globals, whichever executable calls it does, and every kiln executable is fixed-base), so only `print_int.c`'s one embedded `"nil\n"` literal needed real RIP-relative addressing (new `emit_lea_rip_disp32`/`emit_lea_rip_back` primitives). Everything else either had no embedded data or already used relative jumps.
- **B3** `src/elf/elf_so_writer.c` — hand-written ET_DYN ELF64 shared object: SysV `.hash` (not GNU hash — simpler, still what real linkers accept), `.dynsym`/`.dynstr`, no section headers (matches this project's existing "tiny ELF" philosophy; `nm -D`/`readelf` don't need them, only `ld.so`'s own `PT_DYNAMIC`-driven parsing does, and that's section-header-free by design). Exports 5 functions via `codegen/runtime_exports.def` (X-macro, mirrors Plan A's `pe_imports.def` pattern): `kiln_heap_alloc`, `kiln_bytes_copy`, `kiln_string_alloc_prefixed`, `kiln_print_top`, `kiln_raise`.
- **B4** `src/elf/elf_dynamic.c` — the executable side: `PT_INTERP` (real system linker), `PT_DYNAMIC` with `DT_NEEDED=libkilnrt.so` + `DT_RPATH=/usr/local/lib/kiln`, a GOT with eager (non-lazy) `R_X86_64_GLOB_DAT` relocations — deliberately skipped lazy PLT-stub binding (real linkers' default) since it needs a resolver-callback dance with `ld.so` for zero behavioral benefit at kiln's scale. New `emit_call_abs32` primitive (`call [disp32]`, x86-64's absolute-displacement addressing mode) calls through a GOT slot touching **zero** general-purpose registers — necessary because kiln's 5 runtime routines each have their own fixed argument registers (`heap_alloc`: RDI/RAX, `print_top`: RAX/RBX, `bytes_copy`: RDI/RBX/RDX...), so no single register was safe to clobber loading the GOT address first without silently breaking one of them (`bytes_emit_copy` in particular documents RSI as preserved for callers — a register-based GOT-address scratch would have violated that contract).
- **B5** `make install-runtime` (root required, never run by `make all`) installs `libkilnrt.so` to the fixed RPATH.

One real, structural bug found via full-suite testing (not assumed away): the first working end-to-end version crashed on the very first heap allocation. Root cause was a conflated flag — `elf_so_writer.c` temporarily forced link mode to `static` while compiling the runtime, so that the runtime's own internal calls (e.g. `string_alloc_prefixed` calling `heap_alloc`) would resolve as local same-`.so` calls instead of GOT calls back into itself — but `codegen/layout.c`'s globals-address selection reads that SAME flag, and forcing it to `static` also silently made the runtime compute the WRONG globals address (the static-executable layout instead of the shared one) for its own heap pointer. Fixed by splitting into two independent flags (`KilnLinkMode` for "which layout owns the globals", `kiln_is_compiling_so()` for "should this routine's own calls be local or GOT-based") — the two questions looked identical but weren't.

Verified for real, not assumed: 29/30 `kiln/tests/*.ash` byte-identical between `--link=static` and `--link=shared` output (the 1 "difference," `argv.ash`, is `argv[0]` correctly reflecting each binary's own distinct filename — not a bug). `ldd` on a `--link=shared` binary shows the real `libkilnrt.so` dependency; `/lib64/ld-linux-x86-64.so.2` loads and resolves it with zero kiln-side involvement at runtime. Full 30/30 static-mode and Windows-target regression confirmed unaffected.

**Not done: Windows DLL equivalent.** Flagging honestly rather than claiming completeness — this needs (a) a full PE *export* table writer (new, `pe_writer.c` only ever wrote *import* tables before) and (b) generalizing `pe_writer.c`'s import-table layout to support a second imported DLL (`libkilnrt.dll` alongside `kernel32.dll` — currently hardcoded for exactly one). Comparable in scope to B3+B4 combined, not a quick extension, even though the *design* is proven out by the Linux work and Plan A's existing IAT/`win_call.c` machinery gives a clear analogous path. Left for a dedicated follow-up session rather than rushed.

## 2026-07-20 (Plan B, phase B1 — kiln intra-binary runtime deduplication)
First step of "shared runtime library": before a runtime can be shared ACROSS binaries (B3+), the copy inside ONE binary needed to stop being duplicated at every call site in the first place — investigation found kiln's codegen re-emitted several "runtime" routines' full instruction sequences inline at every use (e.g. `heap_emit_alloc`'s 4 instructions at all 27 of its call sites, `codegen_print_top`'s ~150-instruction number-formatting routine at every single `print` statement in the user's source). One real bug hit and fixed during this: converting `codegen_print_top` initially left a stray leftover `pop rbx` inside the shared routine body (an artifact of a multi-step edit that only removed one of the original two `pop` instructions) — since the caller now pops the value into registers *before* the `call` (a real `CALL` pushes a return address on top of whatever's already on the stack, so a `pop` inside the callee would grab the return address instead), that leftover pop corrupted the stack and crashed on the second-ever print statement. Caught via a minimal 2-statement repro + hand-disassembly, not assumed away.

## 2026-07-18 (M8)
Kiln milestone 8: closures / first-class functions. Lambda literals (fn(params){body} as an expression), named functions used as bare values, and calls through a variable all flow through one uniform TAG_FUNCTION runtime shape -- a small, never-resized heap object: [0]=absolute code address, [8]=capture_count, then each capture's (tag,payload). A named function referenced as a value is just a zero-capture closure; codegen_indirect_call never special-cases zero captures, it runs a genuine 0-iteration runtime loop.

Two real design problems solved before writing any code (see codegen/closures.c and lambda.c headers for the full reasoning): (1) a lambda's code address isn't known until after its body compiles, but the closure-creation code that embeds it runs first -- solved with a new "patchable imm64" primitive (emit_mov_reg_imm64_patchable / emit_patch_imm64), generalizing the project's existing emit-now-patch-later jump pattern to an absolute-address immediate. (2) capture_count is only known at runtime (read out of the closure object) and must survive the indirect `call` instruction, but every GP register is freely clobbered by the callee -- solved with a new fixed RBP-relative scratch slot (KILN_FRAME_RESERVE, one slot beyond the normal MAX_KILN_VARS table) rather than the CPU stack, since pushing extra data there would have shifted every existing parameter-offset formula the callee's prologue relies on.

Captures are snapshotted BY VALUE at closure-creation time (documented scope limit, same spirit as M7's linear-scan map note) -- every currently-visible outer variable is captured automatically, no free-variable analysis needed given the single-pass architecture. This supports partial application / currying and higher-order functions (a function returning a closure, a closure passed into another function) but not a closure that mutates a captured variable and expects that mutation visible on the next call (the classic "counter" idiom) -- that needs real upvalues (boxed variables), which conflicts with kiln's single-pass fixed-stack-slot variable model and is out of scope here.

New src/codegen/closures.c (object creation, named-function values, indirect calls) and lambda.c (lambda literal parsing/codegen), split to stay under the 200-line guideline. codegen_call in expr_call.c gained one new branch (variable resolves before function-name resolves) ahead of its existing direct-call path, which is otherwise untouched.

Verified: zero regression on the entire M1-M7 suite, plus a lambda assigned to a variable and called, a named function passed as a value and called indirectly, make_adder-style closures capturing a parameter (add5/add10 independently correct), a closure capturing two outer variables (make_scaler), and a closure passed into a higher-order function (apply_twice(square, 3) = 81).

## 2026-07-18 (M9)
Kiln milestone 9: try/catch. A hand-rolled setjmp/longjmp equivalent, since this is a freestanding binary with no libc to call into -- a fixed-depth (MAX_KILN_TRY_DEPTH=16) handler stack living in the globals region (elf/elf_writer.h), each entry {saved_rsp, saved_rbp, catch target address, error-variable rbp-offset}. Every existing runtime error (array bounds, missing map key) now routes through one reusable "raise" routine (codegen/errors.c) instead of unconditionally dying: if a try is active it pops the innermost handler, restores RSP/RBP to their try-entry values (discarding however deep the call stack had gotten, including through function calls -- verified with an error raised inside a called function, unwinding cleanly back to the try), binds the message as a real TAG_STRING value at the handler's recorded slot, and jumps to the catch block; otherwise it falls through to the original write-to-stderr-and-exit(1) path, unchanged.

Two forward-reference problems, both reusing machinery already built for M8's closures rather than inventing new patterns: the catch block's absolute code address isn't known until after the try body compiles, so it's written via the same patchable-imm64 primitive lambdas use; and the catch variable's slot has to be reserved (for its rbp-relative offset, embedded into the handler struct at try-entry) before its real name is even parsed (`catch (e)` comes after the try body) -- solved with a new small vars.c primitive, rename_var, that reserves a placeholder slot up front and retroactively overwrites its name once `(e)` is seen.

Real bug caught during verification: a caught error's message was initially embedded as raw bytes for a direct syscall write, not as a proper length-prefixed string -- printing a caught error value directly (`catch (e) { print e; }`) read the 8 bytes before the message as its "length" and dumped raw code-segment bytes. Fixed by giving error messages the exact same length-prefixed layout codegen/strings.c's literals use, so a caught error is a fully legitimate string usable with print/concat/equality like any other.

New: a bounds check on the handler-stack push itself (exceeding MAX_KILN_TRY_DEPTH is treated as an unconditional fatal error, never catchable -- silently overflowing past the fixed table would corrupt the adjacent, writable code segment). Verified with a recursive function pushing a try 20 levels deep, dying cleanly instead of corrupting memory.

Scope trim: no explicit `throw` statement -- this milestone catches kiln's own existing runtime errors (array/map), not user-raised ones; deferred alongside the other scope trims already on record (M6's map/filter/reduce, M7's keys/values).

Verified: zero regression on the entire M1-M8 suite, plus catching an array-bounds error and a missing-map-key error (with normal execution continuing after each), a try whose body raises nothing (catch correctly skipped), nested try/catch (inner catches its own error, outer's handler correctly left untouched), an error raised deep inside a called function unwinding back to the try, and the uncaught (no try present) path still dying with the same message and exit status as before this milestone.

## 2026-07-18 (M11)
Kiln milestone 11: `for (x in array) { block }` loops. The array expression evaluates once up front; the loop variable is bound to each element via the same var-slot mechanism `let` already uses (an ordinary, reassignable variable inside the body -- reassigning it doesn't affect iteration, matching a plain for-each's usual semantics).

Real design point: the loop's own state (data_ptr, count, running index) needs to survive whatever the body's own codegen does -- including calls, and including ANOTHER for loop nested inside it. Unlike M9's try/catch (genuinely runtime-recursive, needing a runtime-tracked handler stack) or M10's higher-order builtins (never concurrently active within one frame, since source arguments evaluate left-to-right), `for` loop NESTING is fully visible at COMPILE TIME -- nested `for` statements are literally nested calls in this single-pass compiler. So each nesting level just gets its own fixed RBP-relative offset (vars.h's for_level_offset(depth)) computed from a plain compile-time counter, bounded the same way every other table here is (MAX_KILN_FOR_DEPTH=8), rather than another runtime stack. The counter resets to 0 when entering a function or lambda body (mirroring vars_save/vars_clear/vars_restore) since that body gets its own RBP at runtime and can safely reuse the same offsets independently of the enclosing code's own nesting depth.

Verified: zero regression on the entire M1-M10 suite, plus a basic loop, nested for-in-for (i*j over two arrays), a loop body calling a higher-order builtin (map) without corrupting the outer loop's own iteration state, an empty array (body never runs), a for loop inside a recursive-capable function, and loop-variable reassignment inside the body not affecting which elements get visited.

This closes out the full M1-M11 roadmap from the original plan: Kiln now has variables, control flow, functions/recursion, real doubles, strings, arrays, maps, closures, try/catch, the complete ashvm builtin set, and for-in loops -- all hand-written x86-64 codegen and a hand-written ELF writer, zero external tools anywhere in the pipeline.

## 2026-07-20 (block scoping)
Closed missing.md's block-scoping gap: kiln's variable table was one flat, append-only, per-*function* name->slot array -- `if`/`while`/`for`/`try`/`catch` bodies called the shared `block()` helper with no scope bracketing of their own, so a `let` declared inside stayed resolvable for the rest of the enclosing function forever, and re-`let`-ing a name that already existed anywhere in the function REUSED that slot (mutating it) rather than creating an independent inner binding. `for_loop.c`'s loop variable and `try_catch.c`'s catch variable had the identical pattern, declared outside their own `block()` call.
